# Pancake's code shows where it loses time

The code-level study (Serena + clangd, read-only, HEAD `658a6f7aa` on `port/rdna3-decode`) finds that pancake's time goes to four places. The first is **host↔device waits in the decode window**: `combine_cpu_k10_vec4` spins on a host flag over PCIe and takes **38.3% of GPU time** [meas.]. The second is **a slow prefill path that every agent turn falls onto**: deltas of 1.5-3.2K tokens go through the "staged" path, with a `cudaStreamSynchronize` on every MoE layer. The third is **a buffered arena loader on Linux** (33 GiB in 31-41 s [meas.]), probably also the cause of the oomd kills. The fourth is **prompt re-reads caused by the server** (effort at the start of the prompt, the `<env>` block, sub-agent switches), because the daily preset sets no agent options. The best quick wins are small in effort: 87 (`reasoning_tokens`, one line), 88 (agent settings in the preset only), 89 (real bug: the grammar for tool calls is missing on the Anthropic and Responses paths), 78 (env-only A/B for the staged path) and 38 (O_DIRECT, now aimed correctly at `load_experts_gguf`). On the build side, 92 (the build matrix) would have caught today's MMQ-off break. The study **found no wrong output**. It found one functional bug (89), some robustness risks and a structure (an 18,361-line `main`, a 2,443-line `Service`, 872 `STRATA_*` flags with no registry) that slows down any speed work. All findings are already in MOD_PLAN as items 74-95b. Below I put them in a single execution order for this session and a handover list for dan-99. Labels: **[meas.]** = measured number (the source is given), **[est.]** = estimate from reading the code.

## The decode window loses 38% of the GPU waiting for the CPU

On a single GPU, the daily loop is the serial `while (!pl_ran && ...)` loop in `generate.cpp:19016-19554`. The pipelined loop (`--pipeline-windows`) needs a layer split, so it is off. For each of the 48 layers the chain is strictly serial. The GPU runs the part before the doorbell (GDN/attention, router, `route_publish_res`). The host builds the plan (`expert_pool_dispatch_multi`, `expert_source.cpp:4906-5170`) and publishes it in `h_flagA_`. The GPU spins on flagA (`wait_flag_copy_i32`, **26.4 µs/call on average** [meas.]) and computes the VRAM hits, while the CPU pool computes the misses in parallel. At the end, `combine_cpu_k10_vec4<true>` spins on `h_flag_` from thread 0 of **every** block (10×T blocks) and pulls 10 KB fp32 rows from mapped memory. This kernel alone takes **38.3% of GPU time, with an average of 254 µs/call** [meas., rocprofv3 profile] ([decode_path.md](</home/dan/research_notes/Pancake code deep research/decode_path.md>)).

The measured baseline budget shows where the ceiling is. A short window takes **24.8 ms = 15.9 GPU + 5.2 CPU experts + 2.2 draft**. An edit window takes **37.4 ms = 15.8 GPU + 17.4 CPU experts + 2.5 draft** [meas., MOD_PLAN fast-hip]. The profile counts **~1,360 kernels per window, ~28 per layer** [meas.]. Note: the profiler slows decode from 126 to 79 tok/s, so the average gaps of 5.4 µs are inflated. On edit windows the CPU decides the duration. On short ones the GPU and the gaps between launches decide it. One structural detail matters: **the CPU sits completely idle for ~3 ms per window**, during the head, the sync, the commit and the MTP draft. The draft makes a host round trip for each step (`mtp.cpp:1880-1940`). Item 74 targets exactly this: a `min_p` gate on the device launches the round and all step graphs at once, like the `min_p<=0` branch. The gain is small but exact (0.3-0.5% [est.]), and item 10 stays the big variant (1-3% [est.]).

The rest found on decode has small, safe gains. **75**: with `--adapt-every 1`, `generate.cpp:19396` creates a new `std::thread` at every window, although the engine already has a persistent `JobThread` (`generate.cpp:2125`). The gain is 0.1-0.3% [est.], plus less jitter on the main thread. **76**: the main device never gets `hipDeviceScheduleSpin`, so blocking syncs (`verify.cpp:3872`, the end of the draft) use the default HIP wakeup. An A/B would be worth 0.2-0.6% [est.]. The comment at `verify.cpp:3864-3868` says polling cost ~3% on CUDA, so it must be re-measured on HIP, not assumed. The other decode findings are in dan-99's files and are in the handover list below: the final `wait_parked` barrier (`pool.cpp:1373`), the Q2_0 prefetch, the FMA chain in `row_multi<1>`, per-window `getenv` and the serial activation quantization. One interaction found here is worth remembering for the 8/28 A/B: **deferral turns off `ROUTE_PUBLISH`** (`verify.cpp:2355`). That adds ~48 launches per window, which must be accounted for, otherwise the A/B is biased against 8.

## Agent turns fall onto the slower prefill path

The highest-leverage finding on prefill is a settings collision, not a kernel. The fast-hip preset sets `STRATA_PREFILL_CPU_SHARE=0.6` and `_MAX=4096`. `arm_cpu_share` (`prefill.cpp:2970-2998`) then sets `g_stream_min_share = 4096`, so `stream_all_min()` becomes 4096. **Any chunk under 4096 tokens takes the staged path**: MMQ, host-side grouping, **a `cudaStreamSynchronize` on every MoE layer** (`prefill.cpp:4928`, 48 per chunk), a new `std::async` on every layer for the CPU part (5181) and a blocking join at combine (`cpu_fut.get()`, 6110). The deltas of opencode turns are 1.5-3.2K tokens, so **all** of them go through here. Chunks of 4096+ take the fused streamed path (int8 WMMA experts, issuer thread, no per-layer sync). The difference shows in the measurements: **a 4K read runs at 1,757 tok/s, a 32K one at 2,580 tok/s** [meas., `2026-11-08-7900xt-final-suites.txt`]. The staged settings were never measured on the 7900 XT, because there is no CPU_SHARE A/B for this card ([prefill_path.md](</home/dan/research_notes/Pancake code deep research/prefill_path.md>)). Item **78** is therefore an env-only experiment, with no code: `CPU_SHARE=0` and `SHARE_MAX=1024` on an agent session, with a possible gain of 0-15% of re-reads [est.]. Re-reads take **~18% of a turn's time** [meas., MOD_PLAN].

On long, cold prompts, a hidden serial cost is the PLE (n-gram) read. With `--prefill auto:32768`, a 32K prompt is a single chunk. Its gather (16 rows per token, 4 KiB direct reads, single-threaded FP32 decoding) overlaps only with the embedding and layer 0, and at layer 1 it waits (`ple_land`, 3608-3664). On the 3060, PLE took **10.6% of the GPU timeline at 42K** [meas., MOD_PLAN:486]. On the 7900 XT it would be 3-10% on cold 16-32K prompts [est.]. Item **79** starts the gather at request admission, slices it, decodes it on several threads and adds a compact upload compatible with `--ple-io direct` (today `gather_raw_iq4nl`, `ngram.cpp:714`, needs the mapped table). Item **80** caches the hipBLASLt descriptors, which today are created and destroyed on every GEMM call (`gemm.cu:421-423`). On the staged path this means ~720 calls per chunk, that is 7-20 ms of host time per chunk, exactly when the host is on the critical path [est.]. Item 80 also extends the tuning table, which stops at the T=8192 bucket although chunks reach 32768. Item **81** combines 18 (chunk of 64 for GDN) with CU fill: `gdn_wmma_scan_kernel` (`kernels.cu:2006`) launches **48 workgroups on 84 CUs**. The risk is documented: a chunk-64 attempt on V100 was 4-6 times slower [meas., `bench/results/2026-10-02-gdn-chunk`]. None of this should be touched before **82**: the instrumentation already exists (`STRATA_PREFILL_TIMING=1`, PfTimer with 27 phases, `prefill.cpp:3092`, plus `STRATA_TRACE=1`), but it was never run on the 7900 XT.

## The buffered loader costs 31-41 seconds and probably triggers oomd

Item 38 had the wrong target for the daily preset. This is a **correction of 38**. The `packs/iq2_xs` pack has no `experts.bin` and runs with `STRATA_PIN_BY_NEED=1`. The real path is therefore `load_experts_gguf(..., unbuffered, rp, &pad_)` (`expert_source.cpp:6287`), not `load_experts_direct`. The function's O_DIRECT branch is `#if defined(_WIN32)` (5792-5876). On Linux the code reaches `(void) unbuffered;` (5880) and reads buffered with `fread`, on only **6 threads** (`generate.cpp:7712`). The measured result: **33.02 GiB at 0.81-1.08 GiB/s, that is 31-41 s** [meas., log 2026-11-08/09] ([memory_cache.md](</home/dan/research_notes/Pancake code deep research/memory_cache.md>)).

The likely mechanism of the systemd-oomd kills follows from the order of operations. The pin-by-need arena calls `hipHostRegister` on all **11,592 ranges (33,838 MiB)** *before* loading (`pinned.cu:858-947`), so it brings into memory and pins ~33 GiB of anonymous memory from the start. Then the 6 buffered readers pull another ~33 GiB through the page cache. Those pages are charged to the capped.sh scope (`MemoryMax=54G`), PSI rises, and oomd kills the scope after 30 s above 50%. `MADV_HUGEPAGE` with direct compaction during faults also adds to the stall. The mechanism is supported by code and log, but it is **not proven**: a PSI trace for each variant is missing.

The corrected sketch for 38 adds to `load_experts_gguf` a Linux branch mirroring the Windows one. Each thread has its own `O_DIRECT` fd, with a fallback on `EINVAL` to buffered plus `POSIX_FADV_DONTNEED`. The bounce buffer is 4 KiB aligned, calls are retried on `EINTR`, and the data is scattered to the padded offsets through `dst_blob(l,e)`. There are 16 readers, and a short read refuses the arena, so the existing fallback #4846 kicks in. `experts_unbuffered()` (`pinned.cu:1098-1165`) gets the Windows rule on Linux, `file_cache_keeps(avail, arena, need)`. On this machine (~50 GiB free versus 33+33 needed) the rule gives `unbuffered = true`, and `STRATA_UNBUFFERED_LOAD` keeps priority. The `try_direct`/`leave_direct` helper from `conversation_file.cpp:440-452` must be moved into `src/platform`, and `DirectFile::open` must get the same fallback. As a three-line temporary fix, `FADV_DONTNEED` after each buffered `fread` works. Verification: `STRATA_VERIFY_ARENA=1` must give an identical checksum buffered vs direct, and the scope's `memory.pressure` must stay ~0. The estimate is **12-15 s instead of 31-41 s** [est.] and, if the mechanism is confirmed, the end of the oomd kills. This keeps the arena, which on the 3060 gave **75 vs 69 tok/s versus the mmap fallback** [meas.]. Watch ownership: `expert_source.cpp` is also edited by dan-99. The region for 38 (5775-5937) is separate from dispatch (4906-5470), but the change must be announced.

After 38 comes **86** (the first slice of 69). The conversation cache today is **4,096-6,144 MiB**, depending on the page cache left after the buffered load [meas.]. With O_DIRECT, the size becomes deterministic, and the readers can be paused on PSI pressure. The sketch for 39 (disk tier) also goes here, based on the measured sizes of parked images: **~236 MB fixed + 14.2 KB/token** (fit on 540 and 2,584 tokens; ~1.23 GB at 70K [est.]). Resume would take ~1-1.5 s instead of ~70-80 s of re-reading [est.]. **85** moves THP from registration time into a background collapse and tests pipelined registration on Linux, after measurement: on Windows/5070 decode came out ~10% slower. **83** is item 35 built on existing hooks (`STRATA_CKPT_REREAD` with `--adapt-swaps 0`, plus `STRATA_SNAPSHOT_VERIFY`). The UNSW-style off-by-one is already guarded in the code: the prefix is accepted only if it has ≤ n-1 tokens (`generate.cpp:16161-16166`), and the last output never enters the saved list (19419, 19611).

## The server causes re-reads that the engine could avoid

The preset `configs/pancake/flashnext-iq2_xs-fast-hip.json` contains only engine arguments and env, so the server runs on defaults: `effort_position: "start"`, `env_to_user` off, no per-effort caps ([server_agent.md](</home/dan/research_notes/Pancake code deep research/server_agent.md>)). This has three measurable consequences. First: **switching the opencode variant (xhigh/medium/low) re-reads the whole system+tools prefix**, because the Qwen3.8 template puts the effort sentence at the start of the system turn. That would be ~8-15 s per switch [est.]. Second: **the `<env>` block (cwd, date) breaks the common prefix across days and folders**, with ~14K tokens / 8-11 s re-read (the figure comes from the comment in `frontend.py:405-438`, not from a local measurement). Third: opencode sends `max_tokens` 32000, and `answer_room` (`server.py:6520-6528`) already puts an **implicit 24,000-token thinking cap** on every turn and prints a log line on every request. Item **88** fixes all three from the preset alone: `effort_position: "end"`, `env_to_user: true` and `reasoning_budget_by_effort` / `reasoning_budget_grace: 512` / `reasoning_close_retry: true` (item 12, with p99 values from log 73). With `effort_end` on, `render_prompt` renders the template 3 times (5952-5967). That remains to be reduced to a single render.

Item **87** is the cheapest in the whole report. `_run` already counts `done["reasoning_tokens"]` (7310), but `openai_chunks` builds the usage (7767-7770) without `completion_tokens_details`. Add `"completion_tokens_details": {"reasoning_tokens": x.get("reasoning_tokens", 0)}`, and `openai_collect` (7797) copies it automatically for non-stream too. Item **90** is a trap for 71: the `pin=N` primitive exists (`generate.cpp:15881`), but the `pin_sibling` rule (16463) does not park the branch it leaves. For a sub-agent, that branch is the parent's whole conversation (19-41K tokens). If auto-pin were enabled for Qwen without a size threshold, every return to the parent would become a full re-read. Item **91** tightens the wiring: `pancake.service` cannot use capped.sh, because `systemd-run --scope` takes the engine out of the unit's cgroup (Conflicts=, stop and Restart= no longer reach it). The unit sets its own `MemoryMax=54G` and its own `ManagedOOMMemoryPressureLimit`, and `run-pancake.sh` gets a `NOCAP` switch. The strata-coder agent must move from `qwen3.6-35b-a3b` to `qwen3.8-flash-next-iq2_xs`. The per-turn JSONL log is completely missing today, and without it neither 12, nor 31, nor 71 has data. The Python overhead per request is estimated at **60-300 ms, that is 1-5% of a median 6.2 s turn** [est.; the median is measured on the old backend], and must be measured with the `t_parse/t_render/t_encode` fields of the same log before any optimization of it.

It contains three decode loops with copied logic (`apply_pending` at 13020/20748, `adapt` at 13172/20782). `Verifier::record_window` has 1,479 lines and 6 post variants selected by env. `Prefill::run_impl` has 3,224 lines, of which MoE alone is ~1,480. On the Python side, `Service` has 2,443 lines, and `_run` ~810 lines with ~25 `nonlocal`. The C++ code reads **872 distinct `STRATA_*` names** (1,046 `getenv` calls, 369 of them discoverable only by reading the source), and Python another 81 [meas., count from the code]. ## Conclusion

The most useful lesson of the study is that, on this machine, the biggest unexploited gains are not in kernels. They are in **settings that were never measured on the 7900 XT** (the 4096 staged threshold, `CPU_SHARE` 0.6, ring 192 taken from the gfx12 tables) and in **settings that are simply missing from the preset** (effort at the end, `env_to_user`, caps). Both can be decided in a single session, with no code. The heavy code (fusions, GDN chunk-64, MTP overlap) stays valuable, but it is capped by the 38% spin in `combine_cpu`. GPU work makes sense only after dan-99's 46/49/51 chain brings the CPU part under ~15.8 ms on edit windows.

The second lesson is that structure is not an aesthetic problem but an iteration-speed problem. Today's MMQ-off break, the grammar bug on two of three APIs and the preset without agent settings have the same cause: the lack of a single place that declares what exists (build matrix, shared request builder, flag registry and a config schema printed at start). That is why the first structural PRs are also the cheapest (92, 95b, turnlog). Without them, every 1-3% A/B risks measuring a different configuration than the assumed one.
