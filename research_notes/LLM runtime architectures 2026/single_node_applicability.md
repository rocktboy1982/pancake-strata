# Runtime architectures of single-node, single-user LLM engines (2026) and which large-scale serving ideas transfer to pancake-strata

Scope note: target engine = pancake-strata (C++/HIP fork of Strata), Qwen3.8-Flash-Next (125B MoE, 512 experts top-10, hybrid Gated DeltaNet + sparse attention, MTP), one RX 7900 XT 20 GB + Ryzen 7 5700G (8 Zen3 cores, AVX2, no AVX-512/AMX) + 57 GB DDR4, PCIe 3.0. Today: Python HTTP server <-> C++ engine over a pipe; each verify window captured as a HIP graph; CPU worker pool for missed experts; GPU expert cache with adaptive tier; conversation cache parking KV in RAM/disk. Decode ~126 tok/s; GPU work ~64% of a window, CPU experts ~21%, drafting ~9% (figures from the task brief, not independently measured here). Local Strata docs are cited by path; they are first-party measurements from other contributors' hardware unless stated.

Layering used below: (1) survey -> (2) techniques -> (3) mechanisms -> (4) implementations/code -> (5) applicability.

## Q1. How do local engines (llama.cpp, ik_llama.cpp, KTransformers, ExLlamaV3/TabbyAPI, Ollama, LM Studio, MLC-LLM, PowerInfer, MLX, BaseRT) structure their runtime for one user?

### Takeaway
Almost every local engine converges on the same shape: one long-lived native process owning the device, a thin HTTP/API front (often in-process C++ or a separate wrapper process), a "slot" or "job" abstraction instead of a real scheduler, a host-side prompt/prefix cache as the main TTFT lever, and graph capture (CUDA/HIP graphs or a reused compute graph) as the main host-overhead lever. The hybrid CPU/GPU MoE engines (KTransformers, Fiddler, HybriMoE, PowerInfer, Strata) add one more layer: a frequency-based hot/cold split of experts or neurons plus asynchronous CPU-GPU task scheduling that is folded *into* the captured graph. pancake-strata is already structurally at or beyond the state of the art on this axis; the remaining gaps are in the dependency structure (expert deferral) and in cache behaviour for hybrid recurrent models.

### Cited Findings

Layer 1-2: survey of process models and schedulers
- llama.cpp `llama-server`: single process, C++ HTTP server, N "slots" sharing one context; PR #16391 (merged 2025-10-09) added host-memory prompt caching: cached prompts act as extra slots that are swapped into the active context when that saves reprocessing; bounded by `--cache-ram/-cram` bytes (0 disables, -1 unlimited) and by a token cap that defaults to context size. The author reported it "significantly improves" single-slot use without trashing the prompt cache — [llama.cpp PR #16391](https://github.com/ggml-org/llama.cpp/pull/16391)
- A later llama.cpp release fixed `--cache-ram` not being a hard limit (it always kept at least one entry even above the limit) — [llama.cpp release b11642 via newreleases.io](https://newreleases.io/project/github/ggml-org/llama.cpp/release/b11642)
- Mixed user reports: on unified-memory systems the default 8 GB host cache reservation competed with VRAM and was not useful for one user's workload — [r/LocalLLaMA snapshot](https://reddit.sentinel-team.org/posts/1rva8h2/snapshots/2026-03-16T20%3A46%3A16.316967Z)
- llama.cpp merged "llama : reuse compute graphs" (#14482): a `can_reuse()` check lets a stored ggml graph be reused across decode calls instead of being rebuilt — [llama.cpp commit 01612b74](https://app.semanticdiff.com/gh/ggml-org/llama.cpp/commit/01612b74090df592663cfa01f661c9628f403b59). No public tok/s number for this commit was found.

Recurrent state cannot be rolled back, so without a checkpoint at the right position every new turn forces full reprocessing — [llama.cpp issue/PR thread](https://github.meowingcats01.workers.dev/ggml-org/llama.cpp/pull/22534); [LM Studio bug #1818](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/1818)

- ExLlamaV3: recommended server is TabbyAPI (OpenAI-compatible); README lists continuous, dynamic batching; TabbyAPI describes a paged-attention continuous-batching engine (paged parallel batching needs NVIDIA Ampere+) — [ExLlamaV3 README](https://raw.githubusercontent.com/turboderp-org/exllamav3/master/README.md); [TabbyAPI README](https://raw.githubusercontent.com/theroyallab/tabbyAPI/HEAD/README.md)

- BaseRT (Base Compute, arXiv 2607.00501, July 2026): native C++ runtime calling Metal directly (no MLX/PyTorch/CoreML/llama.cpp); self-reported up to 1.56x decode vs llama.cpp and 1.35x vs MLX (Qwen3, Llama 3.2, Gemma 4 on M3/M4 Pro), up to 1.81x prefill on MoE; CLI serves an OpenAI-compatible API; prebuilt engine under a separate license — [HF blog BaseRT release](https://huggingface.co/blog/basecompute/basert-release); [HF papers 2607.00501](https://huggingface.co/papers/2607.00501)
- PowerInfer: hot neurons preloaded on GPU, cold neurons computed on CPU, online activation predictors; up to 11x vs llama.cpp (Falcon-40B) and ~3x (Llama-2-70B) on one RTX 4090; avg 13.20 tok/s, peak 29.08 across models — [PowerInfer arXiv 2312.12456](https://arxiv.org/pdf/2312.12456v1.pdf); [PowerInfer repo mirror](https://gitee.com/xhal/PowerInfer)
- ik_llama.cpp: offers split mode `graph` (graph parallel) in addition to layer split; README warns of issues combining graph mode with partial offload (`--cpu-moe`, `--n-cpu-moe`, tensor overrides) and suggests `-cuda graphs=0` if output is gibberish; users report layer split slightly faster than graph split with offloaded experts — [ik_llama.cpp README](https://github.blesdmm.dns-dynamic.net/ikawrakow/ik_llama.cpp); [r/LocalLLaMA snapshot](https://reddit.sentinel-team.org/posts/1tg37t6/snapshots/2026-05-23T00%3A36%3A34.219378Z)
- llama.cpp v0.7.0 added a GPU cache for host-memory MoE experts (`--moe-cache-mib`, #29887/#30112): experts kept in RAM run on the GPU from a recency (LRU) cache; up to 2.2x decode when experts are offloaded (one PR-author RTX 5090 run, `--cpu-moe` + cache vs `--fit`) — [llama.cpp v0.7.0 release notes](https://newreleases.io/project/github/ggml-org/llama.cpp/release/v0.7.0); [DevelopersDigest write-up](https://www.developersdigest.tech/blog/llama-cpp-moe-offload-n-cpu-moe-vs-moe-cache-2026)

Layer 3-4: hybrid CPU/GPU MoE mechanisms and implementations
- KTransformers (SOSP '25): experts in CPU RAM computed by AMX/AVX-512 fused-MoE kernels, attention/shared experts on GPU; 4.62-19.74x prefill and 1.25-4.09x decode vs prior hybrid systems; Expert Deferral adds up to 1.45x decode (overall 1.66-4.90x) with average accuracy drop within 0.5% — [KTransformers paper PDF](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf)
- KTransformers profiling: Fiddler issues >7,000 kernel launches per decoded token at ~16 µs each (73% of GPU time is launch overhead); llama.cpp ~3,000 launches/token at ~5 µs (still 21% of GPU time); the paper says llama.cpp disables CUDA graphs in hybrid mode to avoid repeated capture — [KTransformers paper](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf)
- KTransformers mechanism for graph capture across CPU work: the per-MoE-layer "submit" (GPU->CPU activations) and "sync" (CPU results back) are wrapped in `cudaLaunchHostFunc` callbacks inside the stream, so the whole one-token decode path, including CPU expert work, fits in a single CUDA graph; +up to 1.23x decode — [KTransformers paper §3](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf)
- Expert Deferral mechanism: per layer k, the top-scoring routed experts are "immediate" (feed attention of layer k+1), the rest are "deferred" and their output is added at layer k+2, relying on the residual stream; not applied at the final layer; configurations evaluated like 6 immediate + 2 deferred, 4+4 for 8 routed experts; raises CPU utilization from <75% to ~100% — [KTransformers paper §4.1](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf)
- KTransformers NUMA-aware tensor parallelism (each socket holds a slice of every expert) gives up to 1.63x on dual socket; shared experts are only ~18% of GPU time in DeepSeek-V3, so shared-expert/CPU overlap alone leaves the GPU idle — [KTransformers paper](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf)
- Fiddler: missing experts are computed on CPU rather than transferring weights (one token per expert in decode, so CPU compute beats PCIe copy); popularity-profiled expert placement — [Fiddler arXiv 2402.07033](https://arxiv.org/html/2402.07033v3)
- HybriMoE (DAC 2025, built on KTransformers): dynamic intra-layer CPU/GPU scheduling, impact-driven inter-layer prefetching, score-based cache; avg 1.33x prefill and 1.70x decode over prior hybrid SOTA — [HybriMoE arXiv 2504.05897](https://huggingface.co/papers/2504.05897)
- MoE-Lightning: CPU-GPU-I/O pipeline with a performance model; up to 10.3x throughput on one T4 for Mixtral-8x7B, but targets batched throughput, not single-stream latency — [search summary of MoE-Lightning](https://arxiv.org/pdf/2402.07033) (secondary; primary not fetched)
- OSDI '26 paper (arXiv 2606.10493, "Achieving Cloud-Grade SLOs for Local MoE Inference through CPU-GPU Hybrid Design"): stream-loading prefill (streams expert weights to the GPU for prefill) at 1,200 tok/s (32K prompt in <30 s), 1,800 tok/s across two RTX 5090s; intra-node prefill/decode disaggregation sharing weights zero-copy and overlapping attention and MoE across two batches (<15% latency increase, +50% throughput under concurrency); AVX-512 FP8 GEMV CPU kernel 4-5x lower CPU latency; decode 28 tok/s INT4 / 21.5 tok/s FP8 DeepSeek-V3 on dual-socket CPU + consumer GPU — [arXiv 2606.10493](https://arxiv.org/abs/2606.10493)

Strata-family facts (local docs)
- Strata batch slots: off by default (one request at a time, queue in the server); `"parallel": N` decodes N conversations in the same verify window; one user alone unchanged (73-74 tok/s) but each slot takes VRAM from the expert cache, costing 11-24% on a 12 GB card — /home/dan/clone-of-d/src/Strata/docs/BATCHING.md
- Strata split serving (prefill engine on one card, decode engine on another, session handed over via RAM, shared expert arena): slower than a plain layer split on every workload on 2x RTX A6000 (8K: 1.16x slower, 32K: 1.48x, chats 1.04-1.30x; 0 of 6 runs faster) — /home/dan/clone-of-d/src/Strata/docs/SPLIT_SERVE.md
- pancake-strata rejected list already includes KTransformers, PowerInfer, MLC-LLM, ExLlamaV2/V3, vLLM, SGLang as bases (keep model in VRAM or need more VRAM/RAM) — /home/dan/clone-of-d/src/Strata/docs/PANCAKE_FINDINGS.md; /home/dan/clone-of-d/src/Strata/MOD_PLAN.md

### Inferences
- Process model: every mature local engine keeps the device in a single native process; the API front is either in-process C++ (llama-server, BaseRT CLI) or a separate process (Ollama Go server -> runner subprocess, TabbyAPI Python -> ExLlamaV3 in-process Python). pancake-strata's Python-server + C++-engine-over-pipe is the Ollama-style model; at ~8 ms per token (126 tok/s) a pipe hop per *token* is cheap if streamed asynchronously, so a rewrite of the front into C++ is unlikely to move decode tok/s; it can only matter for TTFT if the server does per-request tokenization/templating of very long prompts in Python (unmeasured here).
- "Scheduler" in local engines is really slot/session management plus a prompt cache; none of llama.cpp, Ollama, LM Studio, MLX has a SGLang-style scheduler, because with one active request there is nothing to schedule between iterations. The place where scheduling matters for a single user is *inside* a token: CPU-expert vs GPU work ordering (KTransformers, HybriMoE, Strata's CPU pool).
- KTransformers' `cudaLaunchHostFunc` trick is the same idea pancake-strata already uses (verify window as one HIP graph with CPU experts overlapped), so the 1.23x of that paper is presumably already banked. Expert Deferral is the one KTransformers mechanism Strata only has in a weak, opt-in form (`STRATA_VERIFY_DEFER_CPU`, light CPU expert rows a layer late; measured +8% short / -7% edit, lossy) — see Q2.
- Hybrid recurrent models make prefix caching harder for everybody: llama.cpp still struggles with Qwen3-Next reuse in 2026. A conversation cache that snapshots DeltaNet state at turn boundaries (which Strata has, see MESSAGE_BOUNDARY_CACHE) is a genuine differentiator, not a commodity feature.

### Gaps
- No primary documentation of ExLlamaV3's generator internals (job queue, page table, defrag) was retrieved; inferred from a derivative project only.
- MLC-LLM's 2025-2026 runtime (MLCEngine, its process model, microserving API) was not researched in this pass; no sources collected.
- No tok/s number exists publicly for llama.cpp's CPU-side graph reuse (#14482).
- LM Studio's own runtime beyond "wraps llama.cpp / MLX" was not documented in sources found.
- BaseRT numbers are self-reported; an aggregator quotes 6.4x prefill that contradicts the paper.

## Q2. Do large-scale serving ideas (P/D separation, control/execution split, KV tiering/streaming, prefix/radix caching, overlap scheduling, chunked prefill, reasoning-aware scheduling) make sense on one consumer GPU, and for pancake-strata specifically?

### Takeaway
Most of the big-cluster ideas solve *multi-tenant interference* and *iteration-level host overhead at high batch*; a single-user engine has neither problem in its large-scale form. What transfers is (a) the *intra-token* version of overlap/disaggregation (overlap CPU experts with GPU work by loosening dependencies — Expert Deferral, verify-defer), (b) KV/state tiering and prefix reuse keyed to agent turn boundaries (the biggest TTFT lever for agent sessions), and (c) overlap of KV/weight streaming with compute during prefill. Physical prefill/decode separation, chunked-prefill interleaving and reasoning-aware schedulers are mostly irrelevant with one request in flight, and Strata's own measurement shows P/D split losing even with two GPUs.

### Cited Findings

Overlap scheduling / control-execution split
- SGLang v0.4 zero-overhead batch scheduler: runs CPU scheduling of batch i+1 while the GPU executes batch i (idea from NanoFlow), using "future tokens" and CUDA events; Nsight showed no GPU idle between consecutive decode batches; benefit is largest for small models and large tensor-parallel sizes; on by default — [LMSYS SGLang v0.4 blog](https://www.lmsys.org/blog/2024-12-04-sglang-v0-4)
- TensorRT-LLM overlap scheduler: same CPU/GPU overlap, trade-off is one extra decoding step; can be disabled (`disable_overlap_scheduler=True`) — [TensorRT-LLM overlap scheduler docs](https://nvidia.github.io/TensorRT-LLM/latest/torch/features/overlap_scheduler.html)

Prefill/decode separation and chunked prefill
- DistServe: adding one prefill job to a decode batch noticeably raises both TTFT and TPOT (the motivation for disaggregation) — [DistServe arXiv 2401.09670](https://arxiv.org/pdf/2401.09670)
- Intra-GPU P/D disaggregation (Nexus, "Proactive Intra-GPU Disaggregation of Prefill and Decode", arXiv 2507.06608) partitions one GPU between phases for multi-request serving — [arXiv 2507.06608](https://arxiv.org/html/2507.06608v3)
- Chunked prefill (Sarathi-style) smooths TPOT for concurrent decodes at the cost of slightly higher TTFT for the arriving request, and chunked attention costs a small overhead vs one-shot prefill — [DEV: chunked prefill](https://dev.to/ji_ai/chunked-prefill-why-one-long-prompt-freezes-your-llm-server-30e0); [jayantkhd TTFT/TPOT](https://jayantkhd.is-a.dev/blog/llm-hosting/latency-ttft-tpot)
- Local hybrid MoE P/D: arXiv 2606.10493 does intra-node P/D disaggregation with zero-copy shared weights and overlapping attention/MoE of two batches; gains are reported *under concurrency* (+50% throughput, <15% latency increase) — [arXiv 2606.10493](https://arxiv.org/abs/2606.10493)
- Strata's split serving lost on every measured workload (2x A6000), and its doc says it can only pay when one card is clearly better at prefill and the other at decode — /home/dan/clone-of-d/src/Strata/docs/SPLIT_SERVE.md
- Strata batch slots: concurrent agents get much better follow-up TTFT with more slots (16 agents x 3 turns: TTFT 21.2 s -> 5.7 s) but a single user is unchanged and VRAM per slot shrinks the expert cache — /home/dan/clone-of-d/src/Strata/docs/BATCHING.md

KV tiering, streaming, prefix caching
- llama-server host-memory prompt cache (RAM tier as extra slots) — [llama.cpp PR #16391](https://github.com/ggml-org/llama.cpp/pull/16391)
- LMCache supports CPU RAM, local disk, Redis/Valkey, Mooncake, S3 backends for cross-request/cross-session KV reuse — [lmcache-cli on PyPI](https://pypi.org/project/lmcache-cli/0.5.3rc3.dev6/)
- Single-node NVMe study (arXiv 2609.11744, Llama 3.2 3B, vLLM): LMCache and vLLM's built-in CPU offload both cut cache-hit TTFT 2.2-32.8x vs recomputation on long documents; on repeated long prompts LMCache was 206 ms vs 128 ms for vLLM's native offload — [arXiv 2609.11744](https://arxiv.org/pdf/2609.11744)
- Offloading helps most for intermittent/idle sessions where keeping KV on GPU wastes memory — [Modular handbook](https://handbook.modular.com/inference-optimization/kv-cache-offloading/)
- Strata KV prefetch (upload next attention layer's RAM-resident KV on a separate stream during prefill): prefill -5.3% at 32K, -4.1% at 64K, nothing at 8K, no decode change; ~939 of 1,553 ms of serial KV-stage wait moved off the critical path (2x RTX 3080 20 GB, PCIe 3.0) — /home/dan/clone-of-d/src/Strata/docs/KV_PREFETCH.md
- Strata message-boundary checkpoint (save state at the previous turn boundary so an edited last user message reuses history): first edit 17.2 s -> 11.5 s (-33%) combined with 32K chunks; reused prefix 22K -> 32.8K tokens; decode unchanged (97.55 vs 97.60 tok/s); cold 8K requests +0.2 s — /home/dan/clone-of-d/src/Strata/docs/MESSAGE_BOUNDARY_CACHE.md
- llama.cpp checkpointing for hybrid models exists but Qwen3-Next reuse has repeatedly failed in practice — [llama.cpp issue #18497](https://github.com/ggml-org/llama.cpp/issues/18497)

Reasoning-aware scheduling / KV management
- PASCAL (arXiv 2602.11530): separates reasoning and answering phases with different priorities; up to 72% lower tail TTFT while keeping answer-phase SLOs (DeepSeek-R1-Distill-Qwen-32B, multi-request serving) — [PASCAL arXiv](https://arxiv.org/html/2602.11530v1)
- TIP (arXiv 2609.14850): model emits tokens marking reasoning steps as dead and the runtime drops their KV blocks; Pareto-dominates dense and StreamingLLM/H2O on AIME 2024/2025 across accuracy, live KV size, throughput and decode time (requires a model trained for it) — [arXiv 2609.14850](https://arxiv.org/pdf/2609.14850)

Expert-level overlap (the transferable form of "disaggregation")
- KTransformers Expert Deferral: up to 1.45x decode, <=0.5% average accuracy drop, CPU utilization <75% -> ~100% — [KTransformers paper](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf)
- pancake-strata measurement of Strata's `STRATA_VERIFY_DEFER_CPU` (light CPU expert rows consumed a layer late in verify): short 57.7 tok/s (+8%), code edit 69.0 (-7%), output changes; kept opt-in off — /home/dan/clone-of-d/src/Strata/docs/PANCAKE_FINDINGS.md

### Inferences

Judged applicability to pancake-strata (one user, one 7900 XT, 8 Zen3 cores, PCIe 3.0; profile 64% GPU / 21% CPU experts / 9% drafting per window):

| Idea | Verdict | Reason |
| --- | --- | --- |
| Physical prefill/decode separation (two engines, KV handover) | No | Only one GPU; Strata's own two-GPU version lost 4-48% vs layer split. On one GPU there is no second device to hand to, and with one user there is no concurrent decode to protect. |
| Prefill on GPU while decode continues on CPU / "another conversation's decode" during a new prefill | Mostly no | A single user has one conversation in flight. Exception: an agent harness running sub-agents in parallel; Strata batch slots cover that, but each slot costs expert-cache VRAM (11-24% on 12 GB), so only worth it when concurrent requests are the real workload. |
| Chunked-prefill interleaving with decode | No (for interleaving); chunk size still a TTFT knob | Interleaving only protects other requests' TPOT. Chunk size matters for prefill speed and checkpoint placement (MESSAGE_BOUNDARY_CACHE measured 32K chunks better than 16K together with boundary checkpoints). |
| Control/execution plane split (SGLang/TRT-LLM overlap scheduler) | Already done in spirit; small residual | The win comes from hiding per-iteration Python/CPU scheduling behind GPU work. pancake-strata captures the verify window as a HIP graph and its scheduler is C++. Residual: make the server<->engine pipe and any per-token Python work fully asynchronous (stream tokens, never block the engine on the server). Expected gain: low single digits at most (unmeasured). The "one extra decode step" trade-off of TRT-LLM's version interacts badly with speculative verify, where the next window depends on acceptance. |
| Expert Deferral (KTransformers) / verify-defer generalized | Highest-ceiling runtime idea, but lossy and currently blocked on HIP | CPU experts are ~21% of the window and sit on the critical path between layers. Deferring the lowest-scored of the top-10 experts to layer k+2 lets CPU work overlap the next layer's GPU attention/DeltaNet. KTransformers: up to 1.45x with <=0.5% accuracy drop. Local status (MOD_PLAN.md): Strata's light version (`STRATA_VERIFY_DEFER_CPU`) measured +8% / -7% on CUDA and changes output; on HIP it still gives non-finite logits with the ported RDNA3 kernels; MTP_DEFER is already present; DraftExpert-style miss-aware windows were tested and the policy is already optimal; STRATA_POOL_PREREAD (idle workers pre-read next-layer CPU experts) A/B pending. So: fix the HIP non-finite bug first, then measure a "defer only cache-missed, lowest-weight experts" variant as an opt-in lossy flag (MOD_PLAN rule 2), re-measuring MTP acceptance. |

| KV/state tiering VRAM/RAM/SSD (LMCache/Mooncake-style) for agent sessions | Yes, already present; refine policy | The conversation cache parking KV in RAM/disk is exactly this. - The most likely measurable runtime wins for this engine, ranked: (1) a tuned Expert Deferral flag (lossy, opt-in; first fix the HIP non-finite-logits bug in VERIFY_DEFER_CPU), (2) folding MTP drafting into the captured verify graph / overlapping drafting with CPU expert tail, (3) agent-turn-aware cache policy (anticipatory boundary checkpoint, cross-session system-prompt prefix), (4) prefill weight streaming / KV prefetch for TTFT at 32K+. ## Q3. What runtime-level (not kernel-level) changes measurably sped up single-user decode or TTFT on consumer setups in 2025-2026?

### Takeaway
The documented, measured runtime wins in 2025-2026 cluster into four groups: graph capture/reuse (5-20% decode), asynchronous CPU-GPU orchestration for hybrid MoE (KTransformers 1.23x from single-graph capture, up to 1.45x more from Expert Deferral), prompt/state caching keyed to conversation structure (large TTFT wins on hits: 2-33x in offload studies, -33% first-edit time in Strata), and overlap of transfers with compute in prefill (4-5% at long context). Process-model changes (C++ vs Python front, subprocess vs in-process) have no published decode gains for single-user setups.

### Inferences
- For pancake-strata, the decode budget is GPU-bound (64%) with a CPU tail (21%); runtime changes can only attack the overlap between them and the drafting share (9%). The upper bound from perfect overlap of CPU experts with GPU work is roughly 1/(1-0.21) ~= 1.27x if the CPU part were fully hidden; Expert Deferral is the only published mechanism that targets exactly this (inference, not measured).
- TTFT for agent turns is dominated by cache hit/miss on the growing prompt; turn-boundary checkpointing of DeltaNet state plus RAM/disk parking already exists in Strata, so further gains come from policy (where to checkpoint, what to keep, sharing system/tool prefixes across sessions) rather than new tiers.
