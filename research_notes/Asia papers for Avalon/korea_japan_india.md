# Korea / Japan / India university papers (Nov 2022 - Nov 2026) for pancake and Avalon

Scope: university-led or university-co-led work from KR, JP and IN that fits a batch-1 MoE-hybrid engine (Qwen3.8-Flash-Next: Gated DeltaNet + attention, MTP head) on an RX 7900 XT 20 GB, Ryzen 7 5700G (DDR4), with experts tiered across VRAM, pinned RAM and NVMe and CPU-computed misses. Method: ~18 web searches and fetches, run 2026-11-09. Existing /home/dan/reports already cover Fiddler, fMoE, eMoE, MoE-Infinity, ExpertFlow, MoE-Lightning, HOBBIT, QServe, KVQuant, Medusa, EAGLE and FlexGen, and mention Pre-gated MoE once. None of these is repeated here except Pre-gated MoE, which the brief asks about directly.

Coverage: Korean output is strong and mostly comes from three groups: KAIST (Minsoo Rhu, Jongse Park, Joo-Young Kim), SNU (Jaewoong Sim, Jae W. Lee, Jung Ho Ahn, Hyun Oh Song) and UNIST (Ranggi Hwang). I found nothing relevant led by Japan or India. See the Gaps sections.

## Pre-gating / next-layer router prediction: usable at batch 1 to hide CPU or PCIe latency?

### Takeaway
Yes, for prefetching (PCIe uploads, warming RAM/NVMe), but not in its original form. Pre-gated MoE (KAIST-led, ISCA 2024) retrains the gate so block N picks block N+1's experts, and this model has no such trained gate. The training-free version is to run layer N+1's router on layer N's hidden state, and adjacent-layer gate inputs predict well. Fate, which is not Korean (SYSU), reports 97% prefetch accuracy this way. Prediction cannot start CPU expert compute early, because the CPU needs the real input activation. So the gain is limited to the transfer/prefetch share of a miss, not the CPU-compute share, which is about half of decode.

### Cited Findings
- **Pre-gated MoE: An Algorithm-System Co-Design for Fast and Scalable MoE Inference.** Ranggi Hwang (KAIST, first author) with Microsoft Research co-authors; a USTC author is also listed. ISCA 2024, arXiv 2308.12066 (v3, Apr 2024). The gate in block N selects experts for block N+1, so expert weights held in CPU memory can be fetched while block N computes. Reported: only about 23% latency over a GPU-only system holding all experts, 4.2x lower peak GPU memory, and accuracy "comparable" to the original MoE. — [arXiv](https://arxiv.org/abs/2308.12066v3); [ISCA camera-ready](https://www.microsoft.com/en-us/research/uploads/prodnew/2024/05/isca24_pregated_moe_camera_ready.pdf)
- It requires fine-tuning a pre-gate function (an algorithm-system co-design). A training-free successor, MoBiLE (Tsinghua, not in scope), reuses the previous layer's router scores for prefetching and reports a 1.28x average speedup over Pre-gated MoE and 1.21x over AdapMoE on an RTX 4080. — [MoBiLE arXiv 2510.12357](https://arxiv.org/html/2510.12357v1)
- For comparison (not KR/JP/IN, Sun Yat-sen): Fate uses earlier layers' gate inputs to prefetch the next layer's experts with "no additional GPU overhead". It reports 97.15% prefetch accuracy, a 99.08% hit rate with a shallow-favoring expert cache, and up to 4.1x / 2.2x decode speedups on edge devices. — [Fate arXiv 2502.12224](https://arxiv.org/html/2502.12224v2)
- **SpecMoE: Fast and Efficient MoE Inference via Self-Assisted Speculative Decoding.** Jehyeon Bang, Eunyeong Cho, Jinha Chung, Minsoo Rhu (KAIST, lead) and Ranggi Hwang (UNIST; work done at KAIST). DAC 2026, arXiv 2604.10152. The draft model is the MoE's non-expert layers plus a few hot experts pinned in GPU (4 per block for NLLB-MoE). Routes to unpinned experts are redirected through a precomputed expert-affinity table, a temporal replacement policy refreshes the pinned set, and verification coalesces expert migrations over PCIe. Baselines are MoE-OnDemand, MoE-Overlap (an oracular Pre-gated MoE) and MoE-Caching (top 10% of experts on GPU). Results: up to 4.30x throughput over OnDemand on NLLB-MoE, 2.17x on Mixtral-8x7B, 1.42x on Llama-4-Scout, up to 76.73% less CPU-to-GPU traffic, and 2.25x on average with SSD offload. The paper evaluates batch 1 to 256, and the biggest gains come at large batch. Hardware was an H100 96 GB with PCIe 5.0 (64 GB/s) and 2x Xeon with DDR5. No code. — [alphaXiv 2604.10152](https://www.alphaxiv.org/abs/2604.10152.md)
- **InfiniGen** (SNU: Wonbeom Lee, Jungi Lee, Junghwan Seo, Jaewoong Sim; OSDI 2024, arXiv 2406.19707). The same speculate-one-layer-ahead pattern, applied to KV instead of experts. At layer i-1 it predicts layer i's important tokens from layer i-1's attention input, a partial query weight and a partial key cache, then fetches only those KV entries from CPU. Up to 3.00x over prior KV-offload methods. Code: github.com/snu-comparch/infinigen. — [USENIX](https://usenix.org/conference/osdi24/presentation/lee); [arXiv HTML](https://arxiv.org/html/2406.19707v1); [fork pointing to the artifact](https://github.com/deng451e/InfiniGen)

### Inferences
- **Verdict for pancake/Avalon (Pre-gated MoE):** the original method is not applicable, because it needs a retrained gate. The training-free form is: after layer N's attention/GDN output, apply layer N+1's router (a cheap GEMV over 512-dim-scale router weights) to the current residual and get a predicted top-k for N+1. Use it to (a) start the H2D upload of predicted-but-uncached experts from pinned RAM one layer early, and (b) start NVMe-to-RAM reads two or more layers ahead. If pancake already uploads on demand after the real router runs, this hides about one layer's compute time of PCIe latency per miss. Expected gain: real but bounded. With about 44% VRAM caching and a replay-tier hit rate of 79.6%, misses on the PCIe path could drop sharply if the predictor is above 90%. Misses served by CPU compute see no benefit beyond cache warming, because the CPU needs the true input. My rough estimate is a 0-10% decode gain, and only if PCIe upload, not CPU compute, is currently on the critical path. Measure first: log predicted-vs-actual top-k for N+1 on real opencode traces. This is cheap and gives the accuracy number directly.
- Caveat: L3 prefetch, reuse-aware admission and DraftExpert windows have already been tested without gain. Next-layer router prediction is a different signal from those, but it overlaps with any existing "replay tier" predictor. If the replay tier is already history-based next-token prediction, the router-on-residual predictor should be tried as a complementary signal, not a replacement.
- **SpecMoE verdict:** its central trick is drafting with hot experts only and remapping cold-expert routes to affine hot experts. For pancake, that means the MTP/draft pass never triggers CPU experts and substitutes cached experts instead. That is close in spirit to the already-tested DraftExpert windows, which gave no gain. The paper's own gains are concentrated at large batch, so expect little at batch 1. Low priority. The affinity-table remap is the only new piece and could be tested in the draft path alone at near-zero cost.
- **InfiniGen verdict:** low for KV. Qwen3-Next-style hybrids have attention in only a fraction of layers, and KV at 20 GB fits for single-user contexts. Useful only as design precedent for a "partial-weight one-layer-ahead predictor".

### Gaps
- I found no KR/JP/IN paper that evaluates next-layer expert prediction on a hybrid linear-attention (GDN) MoE, at batch 1, on AMD hardware.
- Pre-gated MoE's exact accuracy numbers per model were not extracted beyond "comparable".

## Memory-system ideas (near-memory, bandwidth-aware scheduling) transferable to a DDR4 desktop with CPU experts

### Takeaway
The Korean PIM/near-data line (MoNDE, AttAcc, NeuPIMs, Duplex, Pimba, PIMphony) needs new hardware. The one transferable principle is "compute the expert where it lives and move activations, not weights", and pancake already does that by computing missed experts on the CPU. The SNU SSD-energy study supports keeping the NVMe tier cold. Nothing here offers a drop-in speedup for a DDR4 desktop.

### Cited Findings
- **MoNDE: Mixture of Near-Data Experts for Large-Scale Sparse Models.** Kim, Choi, Cho, Cho, Lee, Sim (SNU, lead). DAC 2024, arXiv 2405.18832. Cold experts run on near-data compute units and hot experts on the GPU, concurrently, which cuts expert-parameter transfers. — [arXiv](https://arxiv.org/html/2405.18832v1)
- **SSD Offloading for LLM MoE Weights Considered Harmful in Energy Efficiency.** Kyung, Yun, Ahn (SNU), arXiv 2508.06978. Compares SSD, CPU-DRAM and HBM residency for expert weights during decode and finds SSD offloading much more energy-hungry. — [arXiv](https://arxiv.org/html/2508.06978v1)
- **Pimba: PIM Acceleration for Post-Transformer LLM Serving.** KAIST (Jongse Park) with Georgia Tech (Divya Mahajan), arXiv 2507.10178 (Jul 2025). Targets SSM, linear-attention and RNN state updates. It finds state updates are costly for per-bank PIM, so it uses State-update Processing Units shared by two banks, with MX-quantized arithmetic. Reports up to 4.1x over GPU (v3; v1 said 3.2x) and 2.1x over GPU+PIM. — [arXiv v3](https://arxiv.org/html/2507.10178v3)
- AttAcc (SNU + UIUC; whole attention block inside HBM) and NeuPIMs (KAIST; NPU for GEMM plus PIM for GEMV) are attributed by an ETRI survey. — [ETRI Trends survey (Korean)](https://ettrends.etri.re.kr/ettrends/217/0905217027/138-146.%20안백송_217호_최종.pdf); [PIMphony arXiv 2412.20166](https://arxiv.org/html/2412.20166v3)
- Duplex (arXiv 2409.01141) pairs an xPU with logic-PIM and routes each layer by operational intensity. It reports up to 2.67x throughput and 42% less energy than GPU systems for MoE+GQA serving. The affiliation was not confirmed by my searches. — [arXiv](https://arxiv.org/html/2409.01141v1)
- A 2025 analysis notes that at low batch, running MoE layers on PIM is more efficient because of the higher memory bandwidth. — [arXiv 2507.15465](https://arxiv.org/pdf/2507.15465)

### Inferences
- **Verdict:** no direct port. Mapped onto pancake, MoNDE's hot-GPU / cold-near-data concurrent split is the existing VRAM-cached plus CPU-computed design. Its contribution is evidence that the design is sound, not a new technique.
- Pimba's observation that the GDN/SSM state update is bandwidth-bound and that quantizing the state (MX) is the lever suggests one software analogue: keep the GDN recurrent state in a lower precision (bf16 or fp8-like) if it is currently fp32. This is untested here, the accuracy risk is real, and the expected gain is small at batch 1 because the state is tiny relative to expert weights.
- The SNU energy result supports a policy of using NVMe for capacity only and promoting experts aggressively into the 57 GB of RAM. That is likely already true.
- For the DDR4 bottleneck (about 40-50 GB/s practical on a 5700G), the only bandwidth lever from this literature is fewer bytes per CPU expert: lower-bit CPU-side copies, as in the next section.

### Gaps
- I found no KR/JP/IN paper on bandwidth-aware scheduling of CPU expert GEMVs on dual-channel DDR4 desktops, for example NUMA-free, AVX2, or CCX-aware thread placement.
- The Duplex and PAPI affiliations were not confirmed.

## Quantization/sparsity, decoding, KV and agent work that fits

### Takeaway
The most actionable item is SNU's Any-Precision LLM: bitplane storage lets one weight copy serve several bit-widths. That could cut DDR4 traffic for CPU-computed experts, or give the MTP/draft path a cheaper copy of the experts, without a second copy in RAM. KVzip (SNU, NeurIPS 2025 oral) fits the conversation cache. Cassandra (KAIST) and BMC (IISc co-author) are weaker fits.

### Cited Findings
- **Any-Precision LLM: Low-Cost Deployment of Multiple, Different-Sized LLMs.** Yeonhong Park, Jake Hyun, SangLyul Cho, Bonggeun Sim, Jae W. Lee (SNU, lead). ICML 2024 oral, arXiv 2402.10517. Post-training "incremental upscaling" from a seed low-bit model. Bitplane (bit-interleaved) storage overlays 3- to n-bit models in the footprint of one n-bit model. A custom CUDA GEMV matches or beats state-of-the-art quantized kernels. Code: github.com/SNU-ARC/any-precision-llm. — [arXiv](https://arxiv.org/pdf/2402.10517); [GitHub](https://github.com/SNU-ARC/any-precision-llm); [SNU news](https://cse.snu.ac.kr/ko/community/news/1164)
- **KVzip: Query-Agnostic KV Cache Compression with Context Reconstruction.** Jang-Hyun Kim, Jinuk Kim, Sangwoo Kwon, Jae W. Lee, Sangdoo Yun, Hyun Oh Song. NeurIPS 2025 oral, arXiv 2505.23416. Code is in the snu-mllab GitHub org; SNU affiliation is likely but not explicitly confirmed. Scores KV entries by how much the LLM needs them to reconstruct the context, so one compressed cache serves many future queries. Reports 3-4x smaller KV and about 2x lower FlashAttention decode latency with small losses, on contexts up to 170K, tested on Qwen2.5, LLaMA3.1 and Gemma3. — [NeurIPS](https://papers.nips.cc/paper_files/paper/2025/hash/f4eaa4b8f2d08edb3f0af990d56134ea-Abstract-Conference.html); [arXiv](https://arxiv.org/pdf/2505.23416v1.pdf)
- **Cassandra: Enabling Reasoning LLMs at Edge via Self-Speculative Decoding.** Soongyu Choi, Yuntae Kim, Muyoung Son, Joo-Young Kim (all KAIST), arXiv 2605.26558 (May 2026, no venue listed). The draft is a training-free subset of the target: Wanda pruning (40%), 4-bit mantissa truncation, and lossless unary or lossy MX exponent compression, so the draft reuses the target's bits. Reports 1.78-2.41x over a bf16 baseline and 1.81x more tokens than EAGLE-3 under a fixed memory budget on Qwen3-8B/4B-Thinking and R1-Distill-8B. The GPU results are simulated (Accel-Sim, RTX 4090-like). No code. — [arXiv](https://arxiv.org/html/2605.26558)
- **Striking the Right Balance between Compute and Copy (BMC).** Co-authored by R. Govindarajan (IISc) with AMD, USC and others, arXiv 2511.12031 (Nov 2025). Lead affiliation not confirmed; it may be AMD/USC-led. For CPU LLM inference, it allocates oversized KV tensors once every r iterations so updates happen in place without copies, then reuses the redundant slots for speculative decoding. — [fugumt mirror of arXiv 2511.12031](https://fugumt.com/fugumt/paper_check/2511.12031v1_enmode); [newx summary](https://newx.sg/paper/detail/1088bb58-f824-11f0-b84c-00163e10baa7)
- Related KAIST/SNU decoding items: a KAIST + Georgia Tech speculative-decoding survey (arXiv 2411.13157), and an ACL Findings 2026 paper (Hanyang, SNU and KAIST authors) on predicting draft acceptance from the drafter's own signals. — [arXiv 2411.13157](https://arxiv.org/pdf/2411.13157v2); [ACL Findings 2026](https://aclanthology.org/2026.findings-acl.1809.pdf)

### Inferences
- **Any-Precision verdict (medium-high, worth a prototype):** store CPU-tier experts in bitplane layout. The CPU path for missed experts reads only the top k bitplanes, for example 3 of 4 bits during MTP/prompt-lookup draft passes or for low-router-weight experts. This reduces DDR4 bytes in proportion to bits read. Verification still uses the full precision, so the output stays lossless. With CPU expert compute at about half of decode and DDR4-bound, reading 3/4 of the bits on draft-only passes could cut those passes' CPU time by about 20-25%. My guess is an end-to-end gain of a few percent to about 10%, depending on draft share. Cost: an AVX2 bitplane GEMV kernel, because the repo is CUDA, and a matching HIP kernel if used on the GPU tier. Risk: bitplane GEMV on AVX2 may not beat a well-tuned Q4_K/Q8 kernel, so benchmark the kernel alone first.
- A cheaper related idea: router-weight-aware precision. Compute low-gate-weight missed experts at lower precision. This is lossy unless restricted to drafting.
- **Acceptance-prediction verdict (low-medium):** a cheap stop-drafting-early signal could save wasted MTP/prompt-lookup verify work, particularly CPU expert work on rejected tokens. The paper's numbers were not extracted.
- **KVzip verdict (low-medium):** for long opencode sessions, compressing the reusable conversation-cache KV 3-4x could fit more cached conversations or longer contexts. In a hybrid model only the attention layers have KV, and GDN state is fixed-size, so decode-speed gains are small. The value is capacity. Lossy, so evaluate on coding tasks before adopting.
- **Cassandra verdict (low):** pancake already has an MTP head plus prompt lookup. A self-speculative pruned draft would contend for the same VRAM and DDR bandwidth. Its "draft reuses target bits" principle is the same as the Any-Precision idea above, which is the better route.
- **BMC verdict (low):** pancake's KV is GPU-resident. Only relevant to CPU-side copy overheads during speculative verification, if any exist.

### Gaps
- **Japan:** my searches found no University of Tokyo, Kyoto, Science Tokyo, RIKEN or NII/LLM-jp paper on MoE offload, CPU/GPU hybrid inference, speculative decoding or kernels that fits. LLM-jp and Swallow work is mainly model training and corpora, which is not relevant here. A deeper author-level search, for example via DBLP, may surface systems work I missed.
- **India:** apart from the IISc co-authored BMC paper, I found no IISc, IIT or IIIT-H paper in scope. Microsoft Research India (Sarathi-Serve and similar) is a company lab and excluded by the brief.
- Korean MoE quantization work from POSTECH, Yonsei or UNIST did not surface. The MoE-quantization results I found were PKU, SJTU or HKUST, so out of scope.
- KVzip's SNU affiliation and BMC's lead institution were not explicitly confirmed by the pages I fetched.
