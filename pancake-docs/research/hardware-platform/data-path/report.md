# The edit window loses time in overlap, not in bandwidth

On pancake's hardware data path, the main problem is not bandwidth but scheduling. The **37.4 ms** edit window is almost exactly the sum of its parts: **GPU 15.8 + CPU experts 17.4 + draft 2.5 ms**, plus ~1.7 ms of sync. With perfect overlap, the same components would fit in **~20 ms** ([profile-fasthip][pf]; [grouping][tg]). Every hardware link already has headroom. The Q2_0 kernel on the CPU runs at **~80% of the 33 GB/s of DDR4**, i.e. in the same 80–90% band that Intel reports for the best 2-bit GEMV on x86 ([arXiv 2508.06753](https://arxiv.org/html/2508.06753v1)). PCIe promotions reach ~93% of the Gen3 link (115 µs against 107 µs theoretical). At `--pcie-frac 0`, the only transfer on the critical path is the GPU pulling the CPU's fp32 rows in `combine_cpu`, not the expert upload. The resulting order is this. First come the operational fixes that do not touch decode: the direct loader on Linux (item 38), which explains the 28–65 s starts and probably oomd, then the IOMMU guard (54). Next is a single batch of GPU measurements (items 49, 50, 44 and the micro-test from 47), which decides what is worth building. Then come the cheap exact changes: a single poller (46), software prefetch in the Q2_0 kernel (40), the minimum thread count that saturates DDR4 (41) and fusing the pre-doorbell chains (48). Only at the end come the measurement-gated items: pre-summing the rows (51), push through ReBAR (52), Infinity Cache warming (47) and the online swap budget (53). In parallel, the dan-cd session receives the spec for the overlap simulator (42, 43), and parked conversations get an automatic disk tier (39). The important correction in this round is that **the GPU kernels before the router doorbell are on the critical path in both window types**, not only on short chat, as earlier reports said. The items in this round are exact, and their estimated gains (a few percent each) do not add up past the ~20 ms floor. The big lever remains deferral (item 8).

Conventions. "Item N" points to the list in [MOD_PLAN][mp]. Items 38–54 were added on 2026-11-09 from this round. "Exact" means the same greedy text as the base. **[M]** marks an item that needs a measurement first and is not built before it. Gain numbers are estimates from the research notes, not measurements, unless it says "measured". Families F1–F10 are the ones in [Grouped technologies for pancake][tg].

## 37.4 ms is a sum: the critical path goes through the GPU before the doorbell

The host timer, in a run without a profiler, splits the edit window like this: **"GPU-reach wait" 15.75 ms** (how long the host waits for the GPU to reach the router doorbell) and **"per-layer host" 17.94 ms**, of which 17.41 ms are CPU experts. On the short window, the same numbers are 15.93 and 5.59 ms ([profile-fasthip][pf]). "GPU-reach" stays practically constant, even though the VRAM-expert phases grow from 3.25 to 4.26 ms. This shows that each layer's chain is *[GPU before the doorbell: GDN/QSA, hyper-connection, router, publish] → [CPU experts ‖ VRAM hits] → combine*. The VRAM hits stay hidden behind the CPU, but everything that runs before the doorbell adds up ms by ms in both windows. The claim from earlier reports, "a 10% faster GPU gives ~0 on edits", stays true only for the VRAM expert kernels. For GDN, hyper-connection and the router it is false. Concretely, the Q2_0 down kernel (5.79% of GPU time) is worth less per window than the 0.3–0.6 ms estimated before, and fusing the pre-doorbell chains (item 32, re-evaluated as item 48) is worth more.

The same frame explains the **38.3%** of GPU kernel time that shows up in `combine_cpu_k10_vec4`. The rocprofv3 profile gives **254 µs average per call, but a minimum of 5.6 µs** ([run_kernel_stats.csv][ks]). The minimum is the cost of a call when the CPU has already finished, i.e. the zero-copy read plus combine. So **≥97.8% of these 38% is waiting for the CPU**, not compute and not transfer. The GPU gap that can be filled is the difference between CPU and hits per layer: ~40 µs on the short window and **~275 µs on an edit**. Only work that does not depend on the current layer's output fits there.

The three-roof roofline (the method from MoE-Lens, University of Michigan, and the "Amortization Roofline" from MoE-SpeQ, SJTU) shows the same thing. The GPU roof is 15.8 + 2.5 ms, the CPU roof is 17.4 ms (expert bytes at ~27 GB/s), and the PCIe roof is ~0 at `--pcie-frac 0` ([arXiv 2504.09345](https://arxiv.org/html/2504.09345v1); [arXiv 2511.14102](https://arxiv.org/html/2511.14102v1)). Pancake sits on the "sum" line, not on the "max" line. **The ~17 ms missing from every edit window are an overlap problem (F3), not a bandwidth problem (F1).** The 2025–2026 hybrid schedulers all have the same cost shape, min max(T_cpu, T_gpu) per layer: HybriMoE (Peking University, DAC'25), PreScope (NUDT/Tsinghua) and DALI (CAS/SJTU, 1.32x over HybriMoE on an RTX 3090 with PCIe 4.0) ([arXiv 2504.05897](https://arxiv.org/abs/2504.05897); [arXiv 2509.23638](https://arxiv.org/html/2509.23638v1); [arXiv 2602.03495](https://arxiv.org/html/2602.03495v1)). Applied to pancake at batch 1, their placement rule ("GPU if t_gpu < t_cpu") almost never fires, because the CPU does an expert in ~45 µs while PCIe uploads it in ~115 µs. So it is worth modelling in the simulator, but not building into the engine.

## The critical transfer is pulling the fp32 rows, not uploading the experts

Reading the code and sysfs shows that pancake already has all the classic transfer mechanisms: a registered arena (`cudaHostRegister`, hipified), a separate copy stream, DMA, zero-copy aliases, a kernel staging mode, the `strata-fill` promotion thread and doorbells in mapped memory. The effective link to the host is **Gen3 x16** (root port 00:01.1 at 8 GT/s, even though the card's internal switch runs at 16 GT/s). **ReBAR is active (32 GB BAR0)**, and the GPU's IOMMU is in `identity` (passthrough). At `--pcie-frac 0`, the transfer that repeats on every layer, on the critical path, is `combine_cpu_k10_vec4` reading **a full fp32 row (2,560 floats, 10 KB) for each missed (token, expert) slot** from the mapped buffer `h_ymiss_` ([native_moe.cu:145-200][nm]; [verify.cpp][vf]). Under `STRATA_WAIT_FUSE`, thread 0 of *every* block spins on the same host flag. The grid has 10 blocks per token, so ~50 concurrent pollers on PCIe per window, exactly while the CPU pool consumes ~27 GB/s of DDR4.

How much the row pull costs is still disputed, and one measurement settles it. The PCIe-side estimate (~10–20 rows of 10 KB per layer at ~12 GB/s) gives **0.4–0.8 ms per edit window**. The GPU-side estimate uses the 5.6 µs per-call minimum and gives at most **~0.27 ms per window**. But that bound is computed on a profile dominated by short windows, so on edits it may be exceeded. Item **50 [M]** separates the spin from the row pull by running combine with the flag already raised. If the pull stays under ~3 µs per layer, items 51 and 52 are worth ~0. The zero-copy literature supports the direction: EMOGI (UIUC, PVLDB'21) and PyTorch-Direct reach **93% of DMA bandwidth** only with 128 B-aligned, coalesced access ([arXiv 2006.06890](https://arxiv.org/pdf/2006.06890v1); [arXiv 2103.03330](https://ar5iv.labs.arxiv.org/html/2103.03330)). Lustig and Martonosi (Princeton, HPCA'13) already proposed full/empty bits for fine-grained CPU-GPU sync ([hgpu](https://hgpu.org/?p=8831)). Pancake already has this protocol through the partial and A/B/CPU flags, so only the "pull" direction is left to tune.

Four items follow from this analysis, in order of cost. **Item 46** (exact, ~20 lines): block 0 polls the host flag and publishes a flag in VRAM, which the other blocks watch in L2. The test is a `STRATA_WAIT_FUSE` 1 vs 0 A/B that tracks the host's "CPU 17.41" number, not just tok/s, because the hypothesis is that the polls disturb the pool. The estimated gain is 0–3%. **Item 51 [M]**: the CPU pre-sums each token's missed rows (Σ w_e·y_e), so combine reads a single row per token instead of up to 10. That means 2–4x fewer bytes and 0.5–1.5% on edits. The fp32 summation order changes, so the result is no longer bit-identical. The bf16 variant goes through the quality gate. **Item 52 [M]**: the CPU writes the rows and the flag directly into fine-grained VRAM through ReBAR, with write-combining stores and `sfence`. The estimated gain is 1–2% and it overlaps with 51. The risks are WC ordering across 16 threads, the fact that ROCm 10 support on gfx1100 is not verified, and the unknown bandwidth of CPU writes into the BAR on Gen3. The GPU side of the research rates it low value (≤0.27 ms), so 52 comes last and only if 51 is not enough. Item 46 already covers per-block polling. **Item 53**: the swap budget becomes online, after Pie (UC Berkeley, "performance-transparent swapping", up to 1.9x over vLLM on GH200) ([arXiv 2411.09317](https://arxiv.org/html/2411.09317)). Instead of the fixed `--adapt-swaps` values 64/96/160, the budget grows as long as the window stays flat. Promotions are cut into ~256 KB pieces, issued only while the CPU computes, after the paging in MoE-Lightning (Berkeley) ([arXiv 2411.11217](https://arxiv.org/html/2411.11217v1)). Stale entries are dropped from `ForesightSwap::fill_loop`, which today is a FIFO with no staleness check. The estimated gain is 0–5% over the best fixed budget. Its main role, however, is to protect the +5–16% gain from admission (F2) against DMA contention. **Item 54** is a startup log line that warns if the GPU's IOMMU group is no longer passthrough. The Fast & Safe IO Memory Protection paper (SOSP'24) shows that in strict mode, with 4 KiB pages, IOTLB misses become unavoidable, and a 1.4 MB promotion would touch ~344 pages ([UIUC](https://experts.illinois.edu/en/publications/fast-amp-safe-io-memory-protection/)).

## The CPU already sits at the DDR4 ceiling, so only the last percent remain

The Q2_0 kernel in `q2_avx2.cpp` uses exactly the design Intel declares the winner for 2-bit GEMV: up-convert to int8 and VNNI FMA (`vpdpbusd`, with a `maddubs`+`madd` fallback). Intel reports for this design **10–20% below the measured roofline** on the Core Ultra 9 285K and 255H ([arXiv 2508.06753](https://arxiv.org/html/2508.06753v1)). Pancake is at ~80%, so the kernel's arithmetic is no longer a lever. LUT methods win on ARM and at 1 bit, not at 2 bits on x86. Vec-LUT (MobiSys 2026) amortizes the table over parallel tokens ([arXiv 2512.06443](https://arxiv.org/abs/2512.06443v2)), and pancake already gets the same effect with `row_multi<NT>`, which reads each weight row only once for up to 4 verify tokens. Hence the "do not build" verdict for T-MAC, Vec-LUT and any bit-serial rewrite.

Of the last ~20%, three small exact levers remain. **Item 40**: `_mm_prefetch` 1–2 KB ahead in `row_multi`. The Q2_0 kernel has no software prefetch, although the IQ kernel does (`iq_avx2.cpp:201`). Hardware prefetchers stop at the 4 KB boundary ([Intel manual](https://www.manualsdir.com/manuals/127794/intel-architecture-ia-32.html?page=309)), and a gate/up row is 720 B, so a thread crosses a boundary every ~6 rows, in tasks of a few tens of KB. The estimated gain is 0–5% of the 17.4 ms (0–0.9 ms per window), for an hour of effort plus an A/B, with the distance tunable from env. **Item 41**: the minimum thread count that saturates DDR4, run with `STRATA_POOL_FUSE_PHASES`, and the cpufreq `performance` governor (owner decision), 0–3% each. With ~5 MB per phase, a phase takes ~0.19 ms, so a fixed 5–10 µs cost for wakeup, queue and barrier means 2.5–5% of the phase. The fact that 6–12 threads give the same result is exactly the saturation signature described in Arm's roofline guide ([Arm](https://learn.arm.com/learning-paths/cross-platform/llm-decode-roofline/how-decode-uses-memory/)). So the target is window variance, not the mean. The mobile DVFS study (MLSys 2026) finds that the CPU governor underclocks when CPU utilization is low during GPU-driven inference ([arXiv 2507.02135](https://arxiv.org/pdf/2507.02135)). The pool's short phases may start at low frequencies. Per-expert barriers (item 29, Tsinghua OSDI'26) stay with dan-cd, and 41 must be measured with them on. A detail for the platform round: Zen 3 has no AVX-VNNI, so on the 5700G the fallback runs with 2 extra uops every 32 bytes.

Huge pages are already handled correctly: `pinned.cu` tries 2 MiB hugetlb, then conditional THP, with guards against compaction stalls (#771, #2126). The current log says, however, "MAP_HUGETLB unavailable (needed 16920 2 MiB pages)", and THP is only requested. The real problem on the CPU/RAM path is not the TLB but the arena fill, described in the next section.

## Slow startup and oomd come from the loader, not from ntfs3

The log from 2026-11-09 says it directly: "expert arena read through the file cache (**buffered (not Windows)**)" and "loaded 33.02 GiB at **0.49 GiB/s**". On Linux, `experts_unbuffered()` returns false (`pinned.cu` ~1160), and `load_experts_direct` exists only under `#ifdef _WIN32`. So the 33 GiB go through the page cache into a locked 33 GiB anonymous arena, on a 57 GB machine. That means **~66 GiB demand against 57 GB**: reclaim during the load, a speed that depends on what was already cached (0.51–1.18 GiB/s over 13 starts, a 2.3x variance) and pressure visible to systemd-oomd ([pain points][pp]). As a side effect, free 2 MiB blocks for THP are also missing. The mechanism is an inference from the code and from memory arithmetic, not a measurement.

The fix already exists in the same repo. `src/platform/direct_file.cpp` has a pool of 16 `pread` threads with `O_DIRECT`, with 4 KiB-aligned buffers, and it **already works on the same ntfs3 partition**: the PLE probe reports 33,218 rows/s, "fine". **Item 38** ports the direct loader on top of `DirectFile`: aligned 8 MiB chunks, 8–16 in flight, read directly into the THP arena, with no intermediate buffer. `experts_unbuffered()` must return true when the arena plus the read set exceed MemAvailable, i.e. always on this machine. The academic precedents are ServerlessLLM (University of Edinburgh, OSDI'24, with direct I/O, multiple threads per tier and an SSD→pinned DRAM→GPU pipeline) ([USENIX](https://www.usenix.org/conference/osdi24/presentation/fu)), fastsafetensors (IBM, 4.8–7.5x on load) ([PyPI](https://pypi.org/project/fastsafetensors/)) and Haas & Leis (TU Munich, VLDB'23), who show that the software, not the SSD, usually limits the speed ([PVLDB](https://www.vldb.org/pvldb/vol16/p2090-haas.pdf)). The physical limit is the Kingston NV2 on **PCIe 3.0 x4**, at 3,500 MB/s per spec ([datasheet](https://www.kingston.com/datasheets/SNV2S_us.pdf)). That gives the estimate **28–65 s → ~10–14 s** per start, plus fewer oomd triggers and a predictable start. The interim fix, at XS effort, is `posix_fadvise(POSIX_FADV_DONTNEED)` after each buffered chunk. It removes the double memory pressure, but not the 128 KiB I/Os.

The file system is not the cause. Kernel 7.0 already has the iomap read path in ntfs3 (`ntfs_iomap_*` shows up in `/proc/kallsyms`), and the new "ntfs" driver in 7.1 declares **identical reads** to ntfs3, with its gains in writes and mounting ([patch](https://patchew.org/linux/20251020020749.5522-1-linkinjeon@kernel.org)). **Item 39** moves parked conversations to disk automatically. `conversation_file.cpp` already has 16 MiB `O_DIRECT` writes, fsync and atomic rename, but today they are reached only manually, through `/slots/0?action=save|restore`. `--conversation-disk` exists only in strata-poly, which `run-pancake.sh` refuses on HIP. The literature shows that a RAM+SSD KV store cuts TTFT by up to 87% (CachedAttention, NUS) or by 5.7x against recompute (HCache, Tsinghua, EuroSys'25) ([arXiv 2403.19708](https://arxiv.org/abs/2403.19708v2); [arXiv 2410.05004](https://arxiv.org/abs/2410.05004v1)). The right policy comes from Bidaw (Tsinghua, FAST'26), which uses the model's answer to guess whether the user will come back ([USENIX](https://www.usenix.org/conference/fast26/presentation/hu-shipeng)). For pancake, the rule would be: a conversation that ended with a tool call stays in RAM, and one that ended with a final answer goes to disk first. Restoring a 1.13 GB snapshot would take ~0.5–1 s (estimate). The tier needs a size limit, because D is 91% full. Wear is not a problem: 30 parkings a day use ~2% per year of the 640 TBW. Item 39 waits for item 35 (the restore-equivalence test). **Item 45** covers the free I/O checks: a `STRATA_IO_THREADS` sweep on the PLE probe, `filefrag` on `experts.bin` and on the PLE shard, and reordering PLE by frequency (LLM in a flash, IMPRESS) only after the wait on PLE has been measured.

## The simulator adds where the engine should overlap

`tools/pancake/time_ceiling.py` (item 14) computes the window as `max(gpu + cpu + alpha*dma, dma)`, so it adds GPU and CPU. With this formula it cannot price deferral (8), the rank guard (28), barriers (29), the PCIe split (22) or intra-layer reordering, i.e. exactly the decisions it must support. **Item 42** (spec sent to the dan-cd session, which owns 14/27/30) proposes a max-plus model per layer: T_l = max(G_l, C_l + s), and deferral overlaps C_l over G_{l+1}. The model is calibrated at the same time on ms per window (37.4 / 24.8) and on the 38.3% spin. Before the "≥5%" rule uses the simulator, it must be validated at a 5–9% error, the threshold reached by Vidur (Georgia Tech/MSR, MLSys'24) and LLMServingSim 2.0 (KAIST, 1.9%) ([arXiv 2405.05465](https://arxiv.org/html/2405.05465v1); [arXiv 2511.07229](https://arxiv.org/pdf/2511.07229)). The `alpha` coefficient (DDR contention between the pool and DMA) must be measured locally, because no 2022–2026 paper models it on a system with a discrete GPU. MoE-Lens sees the effect only as an overestimate of its model. **Item 43** feeds `DraftPolicy::seed_costs()` from the simulator. The cost of each extra draft position becomes the CPU time of the *new* experts it adds, computed per context bucket, after the MoE-SpeQ cycle formula with PCIe replaced by the CPU. The table would replace the fixed `kShape` curve measured on an RTX 5070. The gain is 0–5%, exact, and it makes SpecFit (item 36) concrete. **Item 44** is a critical-path pass over the per-layer timers: slack per layer and the answer to "how much does the window drop if part X gets x% faster". The published tools (SKIP, TaxBreak, HTA) work on PyTorch/CUPTI traces and do not support a C++ engine on HIP ([arXiv 2504.11750](https://arxiv.org/html/2504.11750v1)).

### The combined measurement batch for a single GPU session

All **[M]** measurements fit into a single GPU booking, with the server stopped and the load gate on (I5), in three steps. **No new build:** (a) the current preset with per-layer `STRATA_VERIFY_PROFILE`, on an edit window and a short one (the same runs serve I7), reporting "GPU busy = total − calls × (mean − min)" for each kernel that contains a spin. (b) A `STRATA_WAIT_FUSE` 1 vs 0 A/B, reading "CPU ms" from the host (the hypothesis test for 46). (c) 6/8/12 threads with FUSE_PHASES, comparing window variance, plus the `performance` governor if the owner agrees (41). (d) `iostat -x` and the `hipHostRegister` duration at startup, plus the log line about THP (38). (e) A `STRATA_IO_THREADS` 8/16/32/64 sweep on the PLE probe (45). **Separate HIP micro-benchmarks (~30 min, no engine changes):** (f) the bandwidth of GPU←host zero-copy reads, the round-trip latency of one PCIe read and the bandwidth of the CPU's WC writes into the BAR, which gates 52. (g) Combine with the flag already raised, replayed on one layer's rows (50). (h) One layer's pre-doorbell kernel sequence, cold vs replayed immediately (47; the threshold is warm/cold < 0.85). (i) The CPU pool running while `hipMemcpy` H2D transfers continuously, for the simulator's `alpha` (42) and for PREREAD. **With a small build:** (j) the stamps from item 49 and the prefetch distance from item 40 (0/1/2 KB sweep via env), in the same binary. `GPU_MAX_HW_QUEUES` 4 vs 6 is retested only together with a concurrent stream (47). A single step is done offline, without the GPU: the histogram of Q2_0 codes (the entropy), which closes the on-wire compression discussion for good.

It would bring back the launch latency that WAIT_FUSE removed, and callbacks add the OS wakeup. It makes sense only if a concurrent stream (47) is hindered by the spinners. |
| Different spin backoff, `s_setprio` | — | Detection is dominated by the PCIe round trip (≤0.1–0.2 ms per window). The spinners sleep via `__nanosleep(100)`. |
| Persistent "post-doorbell" kernel | FlashDMoE style | That segment is hidden behind the CPU in most layers, and the kernel would hide the profiling stamps. |
| Per-expert DALI placement, in the engine | DALI, CAS | At m ≤ 5 tokens the rule does not fire (45 vs 115 µs). Only as a policy in the simulator. |
| Multi-batch pipelines (Klotski), PowerInfer-2, LIA, MoE-Lens as a scheduler | SYSU, SJTU, UIUC, UMich | They assume batch > 1, phone NVMe or AMX/CXL. Pancake decodes a single stream. |
| Online bandit or BO on the scheduler knobs | BanditSpec, SCOOT ([arXiv 2505.15141](https://arxiv.org/html/2505.15141v1)) | The ~20% run-to-run noise and the non-stationary tier would confuse any bandit. The knobs are tuned offline on the simulator, and only the draft length (DraftPolicy) stays online. |
| Experts on SSD by design | FlashMoE; the energy study ([arXiv 2508.06978](https://arxiv.org/abs/2508.06978)) | The arena fits in RAM, and NVMe is ~8x slower than DDR4. RAM_KEEP=20 decoded ~8% slower (measured). |
| cache_ext (eBPF eviction) | Columbia, SOSP'25 | Needs a modified kernel. Here the practical rule is to keep large loads out of the page cache. |
| io_uring in `DirectFile` | Jasny et al., TUDa/TUM ([arXiv 2512.04859](https://arxiv.org/abs/2512.04859)) | As a drop-in replacement it gives ~1.06x. 16 blocking threads already give QD16, and SQPOLL would burn a core the 5700G does not have free. Re-evaluate only if PLE shows up on the critical path. |
| UMWAIT on Linux | — | On a desktop with a dGPU, the CPU and GPU do not share a power budget. |
| FloE-style lossy transfer | ICML'25 ([arXiv 2505.05950](https://arxiv.org/abs/2505.05950)) | It is a lossy F1 technique and goes through the quality gate; it is not a transfer optimization. |

## Conclusion

The round changes the question: it is no longer "which link is too narrow", but "who waits for whom". Every hardware link has headroom: DDR4 at 80%, PCIe at ~93% on large transfers, NVMe untouched in decode. Yet the window is double what overlap allows. Two things follow. First: no bandwidth technique in this round can move the ~20 ms floor, and their realistic combined effect is a few percent up to ~10% on edits, with deferral (item 8) as the only mechanism that reaches overlap. Second: the GPU work before the doorbell becomes, contrary to earlier reports, a good target even on edits. This makes the fusions (48) and possibly Infinity Cache warming (47) worth more than the VRAM expert kernels the series put first.

The safest gain of the round has nothing to do with tok/s. The direct loader on Linux reuses code that already works on the same partition. It probably cuts 15–50 s from every start and removes the most plausible mechanism behind oomd. Together with the disk tier for conversations, it changes the opencode experience more than any millisecond item. The part that stays truly unknown (how much the row pull costs, how much the polls disturb the CPU pool, and whether RDNA3 keeps the weights in MALL) is settled in a single GPU session, not by another round of reading.
