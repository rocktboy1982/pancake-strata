# Engines, labs and companies speeding up consumer-hardware MoE inference (2025-2026): who does what, and what pancake-strata can copy

Scope: a breadth survey. Other researchers cover CPU kernels, caching, speculative decoding, RDNA3 kernels and PCIe/KV in depth. Target box for applicability: pancake-strata (C++/HIP fork of Niko1221/Strata) serving Qwen3.8-Flash-Next (125B MoE, 512 experts top-10, Gated DeltaNet + sparse attention, MTP head, IQ2_XS) on one RX 7900 XT 20 GB + Ryzen 7 5700G (AVX2) + 57 GB DDR4 + PCIe 3.0. Decode ~112 tok/s, bottleneck = CPU compute of cache-missed experts; prefill ~1,800 tok/s.

What pancake-strata already has (from the local repo, read 2026-11-08, used for the "already has it?" column): hybrid CPU/GPU experts with a dynamic VRAM expert cache and swaps, a learned expert profile at start (+6.7% decode), router lookahead (same picks, +10% decode on mmap'd experts), "finish together" CPU/GPU split (PcieAuto), MTP drafting with a reduced draft vocabulary (from Strata-rdna3), auto n-gram/suffix drafts (DraftPolicy), speculative sampling, grammar inside speculative decoding, Q8 KV, graph-captured expert layers, lossy opt-ins (`--tail-skip`, cache-aware routing `turbo` +25% decode with 2.9% token disagreement), `STRATA_VERIFY_DEFER_CPU` (light CPU expert rows a layer late during verify). Rejected after measurement: Foresight prefetch consumer (0.97x), basalt's two-stage head (~1-2%), per-layer VRAM budgets. Sources: local `MOD_PLAN.md` status table and `docs/PANCAKE_FINDINGS.md` sections 5, 7-10 (local files, not web).

## Q1. Open-source engines: which 2025-2026 MoE features exist, and which give the biggest consumer-MoE wins?

### Takeaway
The 2026 consensus feature set for consumer MoE is: (1) experts in RAM + an LRU/LFRU GPU expert cache, (2) MTP and n-gram/suffix self-speculation, (3) a trained external drafter (DFlash 2) for Flash-Next, (4) fused MoE/DeltaNet kernels, (5) CPU/GPU overlap tricks (KTransformers Expert Deferral, up to 1.45x decode). pancake-strata already has equivalents of (1), (2) and part of (5); the clearest uncopied items are DFlash 2 drafting (+28-39% on code/extract for Flash-Next in ik_llama.cpp, a loss on prose), KTransformers-style Expert Deferral generalised beyond verify, and LFRU/frequency-weighted eviction. Note: llama.cpp's cache uploads misses over PCIe instead of computing them on the CPU, which suits PCIe 4.0/5.0 rigs, not this PCIe 3.0 box.

- PR #29887 measured Qwen3.8-Flash-Next Q4_0 (65.4 GiB experts), EPYC 7742 16 threads, PCIe 4.0 x16, no MTP: RTX 4090 25.0 -> 40.7 tok/s (1.62x, 77% hit, `-cmoe --moe-cache-mib 11000`); RTX 5090 30.8 -> 67.8 tok/s (2.20x, 89% hit, 19 GB cache) — [llama.cpp PR #29887](https://github.com/ggml-org/llama.cpp/pull/29887)

**KTransformers / kt-kernel (Tsinghua MADSys + Approaching.AI)**
- Expert Deferral: reorders expert execution across layers so some CPU expert compute overlaps the GPU's attention of the next layer, relying on the residual connection to tolerate the delay; up to 1.45x decode throughput, accuracy variation < 0.5% (i.e. not exact) — [LMSYS blog, 2025-10-22](https://www.lmsys.org/blog/2025-10-22-KTransformers)
- Other KT techniques: AMX tiling-aware kernels for prefill and AVX-512 for decode (21.3 TFLOPS on one Xeon socket, 3.9x PyTorch); async CPU tasks that do not break CUDA Graph capture (launch overhead from >20% to ~0); NUMA-aware expert split (+63% decode on dual socket); chunked prefill 4096 + mixed chunking; "hot" experts on GPU via `--kt-num-gpu-experts` — [LMSYS blog](https://www.lmsys.org/blog/2025-10-22-KTransformers)
- 2026 changelog: Jan 22, 2026 CPU-GPU Expert Scheduling (GPU expert mask, strategies `uniform`/`frequency`/`front-loading`/`random`, `--init-expert-location activation_stats.pt`, `--kt-enable-dynamic-expert-update`); Mar 26, 2026 AVX2-only CPU backend; Sept 11, 2025 Qwen3-Next support; Oct 10, 2025 SGLang integration; June 30, 2025 3-tier GPU-CPU-Disk prefix cache — [KTransformers README](https://github.com/kvcache-ai/ktransformers); [experts-sched tutorial](https://github.com/kvcache-ai/ktransformers/blob/main/doc/en/kt-kernel/experts-sched-Tutorial.md)
- `--kt-gpu-prefill-token-threshold N` (e.g. 400-512): prompts above N tokens run experts on the GPU (same idea as llama.cpp's offload-min-batch) — [KT AVX2 tutorial](https://github.com/kvcache-ai/ktransformers/blob/main/doc/en/kt-kernel/AVX2-Tutorial.md)
- AVX2 backend supports only BF16, FP8, GPTQ_INT4, RAWINT4 formats (no GGUF IQ2 types listed) and requires an NVIDIA 24 GB+ GPU — [KT AVX2 tutorial](https://github.com/kvcache-ai/ktransformers/blob/main/doc/en/kt-kernel/AVX2-Tutorial.md)

### Inferences
- The llama.cpp/ik_llama.cpp cache **uploads misses over PCIe**. On this box (PCIe 3.0 x16, ~12-13 GB/s practical, vs ~33 GB/s DDR4 measured by pancake-strata's CPU experts) a byte of expert computed on the CPU costs roughly a third of the time of uploading it, so Strata's "compute misses on the CPU" (Fiddler-style) design is the right one here; llama.cpp's 1.6-2.2x headline gains come from PCIe 4.0 and 16-24 GB caches and do not transfer. The 3090 report (1-5%) and 5060 Ti report (1.29x) show the gain shrinks where the baseline was already tuned.
- pancake-strata already matches the cache idea; what it could still take from vLLM/tinyserve is the **LFRU eviction score (freq/age)** if its current policy is pure LRU or timing-driven — cheap (a scoring change), exact (placement only changes speed, though the repo notes CPU vs GPU rounding makes cached runs non-bit-identical), expected gain small (a few % hit rate). Worth an A/B since hit rate drives the CPU bottleneck directly.
- **DFlash 2 for Qwen3.8-Flash-Next** is the single most concrete uncopied speed feature: an existing GGUF drafter, exact (greedy verification), +39% code / +28% extraction / -7% prose on a CPU-MoE setup. Caveats: the measured target was at only ~35 tok/s (more headroom for a drafter than at 112 tok/s), and pancake-strata already gets MTP + n-gram drafting; the gain must be measured against MTP, not against no drafting. Effort: high (a second model's forward pass, KV and verification plumbing in the HIP engine), but the draft model is small and fits in VRAM. A DraftPolicy that picks DFlash on code and MTP on prose matches the per-task results.
- **Expert Deferral** (KTransformers) is a generalisation of pancake-strata's `STRATA_VERIFY_DEFER_CPU` to normal decode: let the slowest CPU experts of layer L finish while the GPU runs layer L+1 attention, adding their output one layer late. Up to 1.45x decode reported, but inexact (<0.5% accuracy variation); it would have to be a lossy opt-in. Since CPU experts are the bottleneck, the overlap ceiling is the GPU-wait share of a window (17.5 ms of 66 ms measured in pancake-strata's 10.1 breakdown, on the 3060).
- ik_llama.cpp's fused DeltaNet and fused MoE kernels are CUDA/CPU; pancake-strata's DeltaNet path already has its own 4-column kernel (x1.38-1.44) and Strata-rdna3's fused DeltaNet megakernel for gfx1100, so nothing obvious to copy there.
- Lemonade's HRX runtime is the one AMD-side item that could matter for prefill on gfx1100 (30-50% claim), but it is a llama.cpp backend, not a kernel library pancake-strata can link; treat as a reference to read, not a port.

## Q2. University labs: who publishes what for consumer MoE inference?

### Takeaway
Academic consumer-MoE work clusters into four ideas, all already present in some form in pancake-strata: CPU computes missed experts (Fiddler, UW), hybrid CPU/GPU scheduling + cache (HybriMoE, PKU; MoE-Infinity, Edinburgh), cross-layer expert prediction for prefetch (FATE), and speculative-decoding-aware prefetch (SP-MoE, MoE-SpeQ). The most transferable new pieces are HybriMoE's dynamic intra-layer CPU/GPU scheduling (1.70x decode vs KTransformers) and FATE's "shallow-favoring" cache. Megakernels (Stanford Hazy, CMU Mirage MPK) target launch overhead on H100/B200, which matters less when the CPU is the bottleneck.

### Cited Findings
- **Tsinghua MADSys + Approaching.AI — KTransformers**: see Q1 (Expert Deferral 1.45x, AMX/AVX kernels, NUMA, CUDA-graph-safe async CPU tasks) — [LMSYS blog](https://www.lmsys.org/blog/2025-10-22-KTransformers)
- **PKU SEC Lab — HybriMoE** (arXiv 2504.05897, DAC 2025): hybrid CPU-GPU scheduler + cache management; 1.33x prefill and 1.70x decode vs state-of-the-art hybrid frameworks (compared against kTransformers and llama.cpp); code github.com/PKU-SEC-Lab/HybriMoE — [papers.cool summary](https://papers.cool/arxiv/2504.05897); [arXiv PDF](https://www.arxiv.org/pdf/2504.05897)
- **UW — Fiddler** (ICLR 2025): CPU executes expert layers on cache misses rather than transferring weights; 1.26x single-batch, 1.30x long prefill, 11.57x beam search — [ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/8cd1ce03ea58b3d7dfd809e4d42f08ea-Abstract-Conference.html)
- **FATE** (arXiv 2502.12224, v2 May 2025): feeds layer L's gate input into layer L+1's gate to predict its experts (97.15% prefetch accuracy) at no extra GPU cost; adds a shallow-favoring expert cache (shallow layers predict worse) reaching 99.08% hit rate; up to 4.1x decode vs load-on-demand, 2.2x vs expert-activation-path — [arXiv 2502.12224](https://arxiv.org/html/2502.12224v2)
- **Edinburgh — MoE-Infinity**: per-sequence activation tracing for prefetch/caching on personal machines, 3.1-16.7x latency gains — [arXiv 2401.14361v3](https://arxiv.org/abs/2401.14361v3)
- **SP-MoE** (arXiv 2510.10302, Oct 2025): prefetches target experts during drafting using draft/target structural match; 1.07-3.5x TPOT; notes MoE + SD multi-token verification aggravates CPU-GPU bandwidth contention — [arXiv 2510.10302](https://arxiv.org/html/2510.10302v2)
- **MoE-SpeQ** (arXiv 2511.14102, Nov 2025): quantized on-device draft predicts future experts, Expert Lookahead Buffer, adaptive governor for draft length; up to 2.34x vs SOTA offloading on Phi-MoE — [arXiv 2511.14102](https://arxiv.org/html/2511.14102v1)
- **MoE-Lightning** (Berkeley Sky, older): CGOPipe CPU-GPU-I/O pipeline with paged weights, up to 10.3x throughput for Mixtral 8x7B on a T4 — throughput/batch-oriented (secondary snippet) — [search summary](https://liner.com/review/hybrimoe-hybrid-cpugpu-scheduling-and-cache-management-for-efficient-moe)
- **SJTU IPADS — PowerInfer / SmallThinker** (arXiv 2507.20984, July 2025): models co-designed for local deployment (4B-A0.6B, 21B-A3B), run on PowerInfer extended with expert prefetching and caching; claims up to 86x decode vs Qwen3-30B-A3B in memory-constrained settings — [arXiv 2507.20984](https://arxiv.org/pdf/2507.20984)
- **Stanford Hazy Research — megakernels**: "Look Ma, No Bubbles!" (2025-05-27) fuses the full Llama-1B forward into one kernel, 78% of H100 bandwidth, >1.5x over existing systems; Sept 2025 TP Llama-70B follow-up; Cohere reports a decode megakernel engine 1.25-1.41x faster than vLLM on H100 — [Hazy blog](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles); [Cohere blog](https://cohere.com/blog/megakernels)
- **CMU (Catalyst) — Mirage Persistent Kernel (MPK)** (arXiv 2512.22219, Dec 2025): compiler+runtime that turns inference into one mega-kernel with an in-kernel SM-level task graph; 1.0-1.7x vs SGLang/vLLM; repo mirage-project/mirage branch `mpk` — [arXiv 2512.22219](https://arxiv.org/html/2512.22219v1)
- **MIT HAN Lab**: QServe (W4A8KV4) and LServe (unified sparse attention for long sequences) are MLSys'25, data-center GPUs; omniserve repo last pushed Mar 2025; no 2025 MoE or consumer-hardware work found — [omniserve summary](https://gittrend.io/repo/mit-han-lab/omniserve); [LServe arXiv 2502.14866](https://www.opentrain.ai/papers/lserve-efficient-long-sequence-llm-serving-with-unified-sparse-attention--arxiv-2502.14866/)
- **Expert-skipping research (lossy)**: HookMoE (EMNLP 2025) cuts activated experts >50%, 1.42x prefill, -2.5% average quality, upper layers need fewer experts; ACE (arXiv 2609.05228) training-free, calibration-free skipping within the router's top-k; "Not All Experts are Equal" (2402.14800) 1.2x on Mixtral with ~2.9 pts loss — [search summary with links](https://arxiv.org/pdf/2609.05228); [arXiv 2402.14800](https://arxiv.org/html/2402.14800v2)

### Inferences
- pancake-strata's router lookahead is a FATE equivalent (same-picks prediction, already on by default); FATE's extra piece is a **shallow-favoring cache priority** (give early layers, where prediction is worse, more resident slots). Cheap to test via the learned expert profile weighting; exact; expected gain small-moderate (only matters if misses concentrate in shallow layers — pancake-strata can check its per-layer miss histogram).
- HybriMoE's main claim over KTransformers is dynamic intra-layer scheduling: deciding per layer per token which missed experts the GPU should fetch vs the CPU compute, balancing both to finish together. pancake-strata's PcieAuto "finish together" (share 0.20-0.25) is a static-ish version; a per-window cost model (PCIe bytes vs CPU bytes vs GPU idle) is the HybriMoE refinement. On PCIe 3.0 the upload side is weak, so gain is probably single-digit %.
- SP-MoE/MoE-SpeQ formalise draft-informed prefetch; pancake-strata already routes draft tokens in its lookahead (MOD_PLAN 10.3 "covered by 10.2"). Nothing new to port.
- Megakernels: pancake-strata's decode window is dominated by CPU experts (38 of 66 ms on the 3060 breakdown), so launch-overhead elimination has a low ceiling; Strata-rdna3's fused DeltaNet megakernel is the relevant local precedent for gfx1100.
- The upper-layers-need-fewer-experts finding (HookMoE) supports a layer-dependent `--tail-skip` (skip more low-weight experts in deep layers) as a better-quality lossy opt-in than a uniform skip; needs KL measurement.

### Gaps
- Harvard, NJU, KAIST (SpecMoE) and PKU beyond HybriMoE: no specific consumer-MoE results found in this session.
- Berkeley/SGLang consumer offload features beyond the KTransformers integration: not found.
- HybriMoE and Fiddler absolute numbers on AVX2 desktop CPUs: not found.

## Q3. Chinese companies: anything applicable to single-user consumer offload?

### Takeaway
Most Chinese-company infrastructure releases (DeepSeek's FlashMLA/DeepEP/DeepGEMM/EPLB/3FS, ByteDance MegaScale-Infer, StepFun Step-3 AFD, Huawei Pangu MoGE) target multi-GPU data-center serving and have no direct single-PC equivalent. What transfers is model-side: MTP heads (DeepSeek-V3, Qwen3-Next lineage, which Flash-Next inherits), the vendors' recommended MTP depths, and the KTransformers/Approaching.AI work covered in Q1. Tencent (DSpine drafter) and Alibaba (MTP recipes) give drafting ideas; nothing found from Moonshot, Xiaomi or Zhipu that is specific to consumer offload.

- **Alibaba Qwen**: Qwen3-Next's native MTP is served with `qwen3_next_mtp` (2 speculative tokens, vLLM) or NEXTN with 3 steps / 4 draft tokens (SGLang >= 0.5.2); MTP not generally available in HF Transformers — [vLLM Qwen3-Next recipe](https://docs.vllm.ai/projects/recipes/en/latest/Qwen/Qwen3-Next.html)
- **Moonshot / Tsinghua — Mooncake + KTransformers**: KTransformers' 3-tier GPU-CPU-Disk prefix cache (June 2025) and Kimi K2/K2.5 day-0 support — [KTransformers README](https://github.com/kvcache-ai/ktransformers)
- **ByteDance Seed — MegaScale-Infer** (arXiv 2504.02263): disaggregated expert parallelism (attention and FFN on different GPUs), ping-pong micro-batch pipeline, M2N comm library (4.2x NCCL throughput), up to 1.9x per-GPU decode, 1.5-2.0x cost reduction in production — [arXiv 2504.02263](https://arxiv.org/html/2504.02263v4)
- **StepFun — Step-3** (arXiv 2507.19427): Attention-FFN Disaggregation; finds attention dominates decode cost as context grows while FFN cost stays flat; 4,039 tok/s/GPU on Hopper at 50 ms TPOT, 4K ctx, FP8, no MTP — [arXiv 2507.19427](https://arxiv.org/html/2507.19427v1)
- **Huawei — Pangu Pro MoE** (arXiv 2505.21411): Mixture of Grouped Experts selects a fixed number per device group, giving zero load imbalance by construction; 1,148 tok/s/card on Ascend, 1,528 with speculative acceleration — [arXiv 2505.21411](https://arxiv.org/html/2505.21411v2)
- **Tencent — DSpine** (arXiv 2609.36173): DFlash-family parallel drafter with causal conditioning at every layer, acceptance 3.77 -> 4.82 on Qwen3-8B, +23% SGLang throughput; released only for Qwen3-4B/8B (as read in pancake-strata's local findings, section 8)
- **Approaching.AI** co-develops KTransformers (see Q1) — [LMSYS blog](https://www.lmsys.org/blog/2025-10-22-KTransformers)
- KTransformers ran DeepSeek-V4-Flash on a single Ascend NPU with CPU expert offload (Aug 16, 2026) — [KTransformers README](https://github.com/kvcache-ai/ktransformers)

### Inferences
- The Step-3 finding (attention cost grows with context, FFN flat) mirrors pancake-strata's own profile (attention 38% of a 42K read in strata-poly); for Flash-Next's hybrid DeltaNet + sparse attention this pressure is lower, which is why long-context decode stays flatter than on full-attention models.
- EPLB's "duplicate hot experts" maps to nothing on one GPU, but its single-node analogue is what pancake-strata already does: pin the hottest experts in VRAM from a profile.
- The vendors' MTP recipes (2-4 draft tokens, top-1 chain) agree with pancake-strata's 3-token MTP block and llamAmpere's adaptive 3-4 depth; adaptive depth remains the only open MTP item from this group (exact, low effort, small gain).
- DFlash-family drafters (Tencent DSpine, DFlash 2 in ik_llama.cpp) are the direction Chinese labs and the community are pushing beyond MTP; for Flash-Next a DFlash 2 GGUF already exists (Q1).

### Gaps
- Xiaomi MiMo MTP, Zhipu GLM MTP, Tencent Hunyuan, Huawei OmniPlacement/xDeepServe: no primary sources found in this session (OmniPlacement search returned nothing); ByteDance ShadowKV/Flux not searched.
- No Chinese-language (Zhihu/WeChat) consumer-offload benchmarks were found beyond a Juejin KTransformers overview mentioning a llamafile backend reading GGUF from AVX2 — [juejin](https://juejin.cn/post/7664427110100680723).
- Exact DeepSeek-V3 MTP acceptance (often quoted 85-90%, 1.8x) not verified in the primary text this session.

## Q4. Western companies: what is published, and where is nothing relevant?

### Takeaway
Western company output relevant to consumer MoE is thin: OpenAI's gpt-oss popularised MXFP4 experts and attention sinks; Microsoft's T-MAC gives LUT-based low-bit CPU kernels (2.8x end-to-end vs llama.cpp on 2-bit, partly upstreamed for prefill); NVIDIA's TensorRT-LLM/Dynamo/NVFP4 and AMD's AITER are data-center or Blackwell-only; AMD's Lemonade HRX backend targets gfx1100 prefill. Nothing relevant found from Anthropic, xAI (beyond open weights) or Meta/Google on consumer MoE offload.

### Cited Findings
- **OpenAI gpt-oss**: MXFP4 experts let 20B run in ~16 GB and 120B in ~80 GB; learned attention sinks for longer context; llama.cpp is among reference implementations — [HF blog: tricks from gpt-oss](https://huggingface.co/blog/faster-transformers); [HF welcome gpt-oss (zh)](https://huggingface.co/blog/zh/welcome-openai-gpt-oss)
- tinyserve uses StreamingLLM (4 sink tokens + window) for flat ~29 tok/s at long context on gpt-oss-20B, lossy beyond the window — [tinyserve README](https://github.com/e1n00r/tinyserve)
- **Microsoft T-MAC** (EuroSys'25): table-lookup mpGEMM without multiplication for 1-4 bit weights; up to 6.6x (avg 3.6x) kernel speedup and 2.8x end-to-end on Llama-2-7B 2-bit vs llama.cpp; N>1 kernels integrated into llama.cpp for prefill — [arXiv 2407.00088](https://arxiv.org/html/2407.00088v2)
- **NVIDIA**: TensorRT-LLM tech blogs report MTP on DeepSeek-R1 (1.78x TPS/user on B200) — [TensorRT-LLM blog](https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog1_Pushing_Latency_Boundaries_Optimizing_DeepSeek-R1_Performance_on_NVIDIA_B200_GPUs.html). NVFP4 and basalt's format need Blackwell sm_120 (local MOD_PLAN non-goals).
- **AMD**: Lemonade is a management layer over llama.cpp/whisper.cpp/sd.cpp with Vulkan/ROCm/CPU backends; 11.9 adds the HRX-runtime llama.cpp backend for gfx1100/gfx1151 with a claimed 30-50% prefill gain; community reports say Vulkan beats ROCm by >20% on some Radeon setups due to a ROCm regression (anecdotal) — [Phoronix](https://www.phoronix.com/news/Lemonade-11.9-ROCm-HRX); [wikidocs (ko)](https://wikidocs.net/blog/@jaehong/10579/); [AMD Lemonade article](https://www.amd.com/en/developer/resources/technical-articles/2025/ryzen-ai-radeon-llms-with-lemonade.html)

### Inferences
- T-MAC is the one Western item aimed at exactly pancake-strata's bottleneck (low-bit weights on a CPU). But pancake-strata's CPU experts already run at ~33 GB/s, close to dual-channel DDR4 limits; LUT kernels cut compute, not bytes, so at IQ2_XS they help only if the AVX2 IQ2_XS dot product is compute-bound rather than bandwidth-bound on the 5700G. Worth a micro-benchmark (the CPU-kernel researcher's territory); expected decode gain 0% if bandwidth-bound.
- MXFP4/NVFP4: no gfx1100 hardware support; not applicable except as a storage format.
- AITER (AMD) targets CDNA (MI300) — not searched in depth; no evidence of RDNA3 kernels.

- xAI: Grok open weights exist but no inference-speed techniques found.
- Meta (Llama 4 MoE), Google (Gemma, speculative decoding research), Microsoft DeepSpeed-MoE/BitNet, AMD GAIA/Ryzen AI, NVIDIA Dynamo: not searched in depth this session; no consumer-offload-specific sources found.

## Q5. Copy map: technique -> who -> already in pancake-strata? -> copy?, with gain, exactness, effort

### Takeaway
pancake-strata already implements most of the field's consumer-MoE playbook (expert cache with CPU compute on miss, profile placement, router lookahead, MTP + n-gram + suffix drafts, grammar-in-spec, deferred CPU rows in verify). The best remaining copies, in order: DFlash 2 drafter for Flash-Next (exact, high effort, +28-39% measured elsewhere on code/extraction), adaptive MTP depth (exact, low effort, small), LFRU / shallow-favoring cache scoring (exact, low effort, small), Expert Deferral in normal decode (lossy, medium effort, up to 1.45x claimed, ceiling set by GPU idle share), layer-dependent expert skipping (lossy, low effort, needs KL).

### Inferences
- Rough sizing for why CPU-on-miss wins here: Flash-Next has 24,576 experts (512 x 48 layers per the Strata articles); at ~120B expert params and 2.31 bpw that is ~1.4 MB per expert, ~670 MB per token if every one of 480 selected experts missed. At a 30% miss rate, ~200 MB per token: ~6 ms at ~33 GB/s on the CPU vs ~16 ms over PCIe 3.0 (~12.5 GB/s). This is an estimate, not a measurement; it supports keeping Strata's design and focusing on hit rate, deferral/overlap and drafting.
- Because decode is CPU-expert-bound, drafting features that verify several tokens per window amortise the CPU's expert reads only to the extent that drafted tokens share experts; DFlash 2's gains were measured with `--cpu-moe`, i.e. exactly this regime, which makes it the most credible transferable result.

### Gaps
- No public measurement of DFlash 2 vs MTP (rather than vs no drafter) on Flash-Next.
- No public HybriMoE / Expert Deferral numbers on an AVX2 desktop with PCIe 3.0.
- pancake-strata's exact eviction policy was not inspected in source (the source tree is under active benchmarking; only docs were read).
