## 1. ThinkBrake, arXiv 2510.00546 (plan item A19)

**Number the plan and notes cite.** Plan candidate list: "ThinkBrake -25% thinking tokens on BFCL non-live". Notes (`notes/agent_thinking_papers.md`, `round2/notes/agent_round2.md`): BFCL non-live base avg accuracy 89.6, ThinkBrake 89.8, -24.9% thinking tokens; BFCL live 82.9 base vs 82.4 ThinkBrake ("a small loss").

**Number in the paper (current PDF, arXiv v5, Apr 2026).**
- Table 15, p.20 (full BFCL-v1 table), Qwen3-4B-Thinking, BFCL-v1 (= non-live) splits:
  - Simple: base 88.2, ThinkBrake 87.3, dTok -32.9%
  - Multiple: base 90.5, ThinkBrake 90.0, dTok -12.4%
  - Parallel: base 93.5, ThinkBrake 95.5, dTok -26.8%
  - Multi-Parallel: base 90.5, ThinkBrake 90.5, dTok -28.2%
  - Mean of the four (our arithmetic from Table 15): accuracy 90.7 to 90.8; token reduction 25.1%. The "Avg." of all ten BFCL/Meta-Tool columns is -22.8% (Table 15).
- Table 2, p.6 (same model, parallel/multi-parallel subset): Parallel -26.8%, Multi-Parallel -28.2% (as above).
- Table 13, p.18: base average thinking tokens, BFCL-v1 Qwen3-4B-Thinking: 1,214 (mean of 1,072 / 965 / 1,199 / 1,621).
- Abstract (p.1, v5): "reducing thinking token usage by up to 30%". Section 4.2 (p.6): math "10-30%".

**Verdict.** VERIFIED for the plan's headline: about -25% thinking tokens on BFCL-v1 (non-live), mean 25.1% in v5.

DISCREPANT for the notes' specific figures. The notes' numbers (89.6 to 89.8, -24.9%, live 82.9 to 82.4) do not appear in v5. They match the earlier v1 PDF (arXiv 2510.00546v1, the BFCL table near lines 194 to 208 of the v1 text: non-live avg base 89.6, ThinkBrake 89.8, -24.9%; live avg base 82.9, ThinkBrake 82.4, -15.3%). The v5 revision changed the numbers:
- Live (BFCL-v2, Table 15, p.20): base 79.8 / 83.4 / 87.5 / 79.2 (mean 82.5); ThinkBrake 82.2 / 82.9 / 87.5 / 87.5 (mean 85.0). So in v5 ThinkBrake is about +2.5 points on live, not a loss. The notes' "small loss on live" statement is out of date.
- Non-live accuracy: v5 mean 90.7 base vs 90.8 ThinkBrake (not 89.6 vs 89.8).

Action for the plan: keep "-25% thinking tokens on BFCL non-live", cite v5 Table 15 (p.20), and drop the v1 accuracy numbers from the notes.

**Setup.** Qwen3-4B-Thinking (also Qwen3-4B, 14B, 32B, DeepSeek-R1-7B, Phi-4-Reasoning, Qwen3-Next-80B) on BFCL v1/v2 and Meta-Tool; baseline = the same model with its own thinking, no early stop; 2x H200 GPUs (p.8 and p.12); single run per table cell (32-run intervals only for AIME).

**Exact or lossy.** Lossy. It stops thinking early at a sentence boundary. Accuracy changes per split (for example Simple -0.9, Multiple -0.5, Multi-Parallel 0.0 on Qwen3-4B-Thinking; Parallel +2.0).

Caveat for us: the -25% is an average of per-split percentages on a 4B model with BFCL-style short function calls. It is not a per-turn time share. It must be combined with the thinking share of turn time (see the plan's A19 row; not checked here).

## 2. Thought Calibration, arXiv 2505.18404 (plan item A19)

**Number the plan and notes cite.** Notes: up to 60% fewer thinking tokens in-distribution, up to 20% out-of-distribution; probes are on PCA d=256 hidden states; the supervised probe is over-confident.

**Number in the paper.**
- Abstract (p.1) and introduction (p.2): "up to a 60% reduction in thinking tokens on in-distribution data, and up to 20% in out-of-distribution data".
- Figure 2, p.7: in-distribution held-out s1K-1.1 split, DeepSeek-R1-distill Qwen 32B, DeepSeek-R1-distill Llama 70B, QwQ 32B; "reduce the number of thinking tokens by over half for all three models, with minimal impact to overall performance"; text on p.7 says the maximum reduction is 60%.
- Figure 3, p.7: Qwen 32B probes applied to AIME 24, GPQA Diamond, MATH 500 (out-of-distribution): "We achieve up to a 20% reduction in thinking tokens."
- p.7 (section 4.3): the probes "improve (AIME 24, GPQA) or match (MATH 500) the efficiency of the budget forcing"; this is an efficiency claim, not an accuracy-gain claim.

**Verdict.** VERIFIED (60% in-distribution, 20% out-of-distribution, both on math and science only).

**Setup.** DeepSeek-R1-distill Qwen 32B / Llama 70B and QwQ 32B; "4 A6000 GPUs using vLLM" (p.6). Math and science only. No tool-use benchmark.

**Exact or lossy.** Lossy (early exit with a calibrated risk bound; the paper's guarantee holds only over draws of the calibration set).

## 3. ECLoop, arXiv 2607.28815 (plan item A41)

**Number the plan cites.** Candidate list: "+4.8 to +11.8 pp on SWE-bench (ECLoop, summary level)". Notes: four configurations, Self-Refine lowers Pass@1 by 1.4 and 1.8 pp; ablation 47 / 63 / 58 / 59 / 68 on a 100-instance subset; tokens down 1.4 to 12.1%.

**Numbers in the paper (SWE-bench Verified, 500 instances, Pass@1).**
- Table 1, p.5, mini-swe-agent v2: GPT-5-mini 56.2% to 68.0% (+11.8 pp, RRU 26.9%); MiniMax-M2.5 75.8% to 80.6% (+4.8 pp, RRU 19.8%). Self-Refine: GPT-5-mini 54.8% (-1.4), MiniMax 74.0% (-1.8). Both ECLoop gains p < 0.001, exact McNemar.
- Table 2, p.6, Codex CLI: GPT-5-mini 40.4% to 50.8% (+10.4 pp); MiniMax-M2.5 (high effort) 74.8% to 79.8% (+5.0 pp).
- Table 3, p.7 (tokens and cost, per instance): mini-swe GPT-5-mini 179K to 157K (-12.1%), cost $0.047 to $0.042 (-10.2%); MiniMax 219K to 206K (-6.2%); Codex GPT-5-mini 111K to 105K (-5.4%); Codex MiniMax 165K to 162K (-1.4%).
- Table 4, p.7 (ablation, 100 instances, mini-swe-agent v2, GPT-5-mini): full 68; minus guidance 63; minus commitment check 58; minus state update 59; baseline (minus all) 47; natural-language spec 58.

**Verdict.** VERIFIED. The plan's +4.8 to +11.8 pp is the range across all four configurations (Table 1 and Table 2: +4.8, +5.0, +10.4, +11.8).

**Setup.** SWE-bench Verified (500 instances), two models (GPT-5-mini; MiniMax-M2.5 at high reasoning effort), two scaffolds (mini-swe-agent v2; Codex CLI). The same model writes the specification, judges gaps and drives the agent. Hardware is not reported in the sections read.

**Exact or lossy.** Lossy: it changes what the agent may do (holds an edit or submission up to three times, then an audited fallback). The paper's own regression cases come from that fallback (9 regressions per run).

**Plan wording to fix.** The paper's gate is on structured evidence conditions derived from the issue and static analysis (AST, call graph, class hierarchy). It is not a plain "read the file before edit" rule. The plan's A41 row ("read-before-edit gate") should say "evidence-conditioned commitment gate". The ablation shows a natural-language summary of the same conditions (58) helps less than the structured version (68), so a prompt-only nudge is not the tested mechanism.

## 4. AsyncFC, arXiv 2605.15077 (plan item A40)

**Numbers the plan and notes cite.**
- SWE-bench Lite 1.40x over SWE-agent, accuracy 79.3% vs 79.0%.
- BFCL v4 Web Search 1.26x; accuracy 53.2% vs 54.8%.
- HotpotQA 1.24x; accuracy 75.0% unchanged.
- BFCL v3 multi-turn with Gemini 3.1 Pro 1.17x; accuracy 62.0% to 65.3%.

**Numbers in the paper.**
- Abstract and p.2 (introduction): "a 1.26x speedup on adapted BFCL v4 Web Search workloads and a 1.40x speedup on SWE-bench Lite".
- Figure 3, p.7 (BFCL v4 Web Search): Seq. FC 54.8% (baseline); AsyncFC (S) 53.2% with speedup 1.26x; Par. FC 50.0%; AsyncFC (P) 50.0% with speedup 1.12x. Also BFCL v3 Multi-Turn (n=150, 5 s delay): Seq FC 68.0%, Par FC 67.3%, AsyncFC (S) 69.3%.
- Figure 5, p.9:
  - Cross-model: BFCL v3 Multi-Turn, Gemini 3.1 Pro (n=150, 10 s delay): Par FC 62.0% to AsyncFC (P) 65.3%, speedup 1.17x (relative to Par FC).
  - SWE-Bench Lite (n=300, GPT-5.6 Sol, real function latency): SWE 79.0%, speedup relative to SWE 1.00; +Par FC 79.0%, speedup 1.04x; +AsyncFC 79.3%, speedup 1.40x (relative to SWE).
  - HotpotQA (n=50, GPT-4o, real function latency): Seq FC 75.0%, AsyncFC (S) 75.0%, speedup 1.24x.
- p.9 text: "AsyncFC achieves a 1.4x speedup over the SWE-agent baseline and a statistically significant latency improvement over +Par. FC". Figure 5 caption: no statistically significant accuracy degradation (all p_acc > 0.05).

**Verdict.** VERIFIED for every number in the notes. Framing corrections:
- The 1.40x is against the sequential SWE-agent baseline. The paper's own parallel-function-calling variant gives 1.04x on the same task. AsyncFC against parallel function calling is therefore about 1.35x (1.40 / 1.04, our arithmetic; the paper does not state this ratio).
- The 1.17x on BFCL v3 is against Par FC, not against sequential calls.
- BFCL v4 Web Search loses 1.6 accuracy points (54.8 to 53.2). The paper calls this not significant; it is not zero.

**Setup.** Hosted API models only (GPT-5.6 Sol, GPT-4o, Gemini 3.1 Pro, a Seq-FC/Par-FC baseline per workload). Hardware not specified (checked: no GPU or hardware line in the paper). Workload delays are injected (5 s, 10 s) in the BFCL runs; SWE-bench uses real latency.

**Exact or lossy.** Lossy. Decoding continues past placeholder values that are not yet known; the paper gives no rollback for a wrong guess. The paper itself does not classify it as exact or lossy. Evidence is task accuracy, not token equality.

## 5. TraceLab, arXiv 2606.30560 (plan item A40)

**Number the plan cites.** Candidate list: "up to 60% of request time is tool time (TraceLab)". Notes: per request tool 59.8%, LLM 41.0%; per step tool 59.3%, LLM 40.7%.

**Numbers in the paper.**
- Table 7, p.6 (wall-clock by category):
  - Per request, response time: total mean 4.3 min (median 38.3 s, p90 6.4 min, p99 43.9 min). LLM generation 41.0% of response time; tool execution 59.8%.
  - Per step: LLM generation 40.7% (mean 11.5 s); tool execution 59.3% (mean 16.8 s).
  - Per session, uncapped: human thinking 92.3%, LLM generation 3.3%, tool execution 4.8%.
  - Per session, human gaps capped at 1 h: human 64.3%, LLM 14.5%, tool 21.2%.
- Text p.6: "of the total 2,783 hours of response time, tools account for 59.8% versus 41.0% for generation".
- Table 1, p.4: 4,265 sessions (2,676 Claude Code from 37 users; 1,589 Codex from 22 users; Sep 2025 to Jun 2026; 23 models).

**Verdict.** VERIFIED as an average share. The plan's "up to 60%" is wrong wording: 59.8% is the mean share of response time across all requests, not a maximum. Per-request shares sum to 100.8% (41.0 + 59.8); the paper does not explain this (consistent with the notes).

**Setup.** Trace characterization of real coding-agent sessions (Claude Code and Codex), API-hosted models; Codex tool time is reported by the tool, Claude tool time is derived from call and return timestamps (paper section 3). This is a measurement paper, not a method.

**Exact or lossy.** Not applicable (measurement).

**Scope warning.** Mixed Claude and Codex traces on hosted APIs. It does not measure opencode or local-model turns, which is what our A40 test must measure.
