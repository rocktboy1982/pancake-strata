# Pancake loses time first in turns, then in kernels

Pancake has two kinds of problems, and they are measured in different units. **In the engine**, a decode window takes **37.4 ms on a code edit**, and **17.4 ms of that (47%) is experts computed on the CPU**. The pool already runs at ~80% of the measured DDR4 bandwidth. So the only gains come from moving fewer bytes off the CPU or hiding them behind GPU work, not from faster math ([profile-fasthip][prof], [MOD_PLAN phase 13][mp]). **In the agent turn**, the opencode history (2,063 Flash-Next turns served by the old backend, not by pancake) shows something else. The median turn is 6.2 s, but **p90 is 50 s and p99 is 224 s**. This tail comes from **prompt re-reads (~18% of total turn time)** and from **uncapped thinking** (15 turns cut at 8K–32K tokens, 2,726 s), not from tok/s ([server_agent_ops][sao]). The biggest practical problem is also the cheapest: **pancake is not yet wired to opencode**. It has no systemd unit, it listens on port 8080 instead of 11437, and the thinking caps, already written in code, are not enabled in any preset. The recommended order is as follows. First the wiring and the caps, at almost no effort. Then the measurements that are still missing (per-turn timeline, profile on an edit window, prefill on the 7900 XT). Then the exact engine levers (the restore test and per-turn checkpoints, admission on the k-th miss, keeping the cache after long prompts, the down kernel for Q2_0). Last come the lossy levers (turbo-hip, which measured **+30–50%**, deferral, sparsity), after the revised quality gates. This report only makes recommendations: nothing it describes has been changed.

A few conventions for the whole report. "Window" means one MTP draft plus verify cycle. "Item N" points to the list of 37 items in [MOD_PLAN.md][mp]. The research series reports are cited by region name (Asia, Europe, USA, MIT, Stanford, Canada, Pacific, Avalon upgrades). The agent numbers come from the opencode database of the old backend (Strata on 11437 or Avalon). They describe the shape of the load pancake inherits, not pancake's performance.

## CPU experts take 47% of the edit window, and the GPU floor dominates short chat

The fast-hip profile splits the window like this. On a short chat it is **24.8 ms**: GPU 15.9, CPU experts 5.2, draft 2.2. On an edit it is **37.4 ms**: GPU 15.8, CPU experts 17.4, draft 2.5, with **357 CPU experts per window** (7.44 per layer × 48 layers) ([profile-fasthip][prof]). Each CPU expert costs ~48.8 µs for ~1.3 MB, i.e. **~27 GB/s against 33 GB/s measured RAM**. So items that only optimize CPU compute (29 barriers, 24 IQ1_M, pool sweeps) can reach at most the remaining ~20% plus the sync overhead. The worker/task sweep confirmed that the defaults are already the best ([pool-sweep][pool]). The rocprofv3 profile of a short request shows that **38.3% of GPU kernel time is `combine_cpu_k10_vec4`, which spins waiting for the CPU rows**, plus 4.1% `wait_flag_copy_i32`. Real GPU work is therefore ~57.6% of kernel time, with 395 kernels per token ([gpuprof][gpu]).

The biggest exact lever is the **expert cache driven by time cost**. The simulator (`tools/pancake/time_ceiling.py`, the Baleen/CMU method) showed that LRU loses ~20% on short chats. Online "second miss in 8" admission gains **+5..16% on edits**, and the tier at every window ×160 gains **+4..9%**; DMA contention decides how much of the gain remains ([PANCAKE_STATUS][ps]; [USA P3/P4][us]; [Europe P5][eu]; [Asia P6][asia]). "Admit on k-th miss" is being written in the engine now, and `--adapt-swaps 64/96/160` waits in the queue. The expert predictors in the literature (ProMoE 1.09×, HOBBIT 4.7–8.7%) were evaluated on models with 8–64 experts and PCIe 4.0. Locally, the history predictors cover only 20–29% of misses, and the Asia report warns that on PCIe 3.0 with CPU compute "most gains vanish" ([Asia][asia]; [MOD_PLAN phase 10][mp]).

The only lever that **overlaps** CPU work with GPU work instead of reducing it is **expert deferral (KTransformers, SOSP'25)**. On DeepSeek-V3 it gave −26% time per layer and +33% decode ([Asia P1][asia]), and the estimate for pancake is **+10–25% on edits**. On HIP, however, `STRATA_VERIFY_DEFER_CPU` still produces **non-finite logits**: the runs measure 0.0 tok/s on short requests and 14–68 tok/s on edits, with one HTTP 503 ([roundA][rA], [roundC][rC]). `cfuse` is already excluded when deferral is on ([verify.cpp:1467-1472][verify]). A static reading of the preset points to the other switches on the combine/hit path as suspects (WAIT_FUSE, ROUTE_PUBLISH, GR_FUSED, QDEDUP, ADAPT_OVERLAP, EXPDEC), but the cause is not confirmed, and the bisect (6 runs) is in the queue. This bug blocks the lever with the highest ceiling in every report of the series (items 8, 28).

**Turbo-hip** (`STRATA_ROUTE_PRIOR 0.5`, cache-conditioned routing, validated in principle by Cache-Conditional Experts, Qualcomm/UvA) is already built and measured: **149–169 tok/s against 128.7 for C-best** ([roundC][rC]; [Europe P1][eu]). On the 3060 it had 2.89% mismatch against 1.17–1.30% between two stock runs, and 0 large-margin events. The router bias in upstream Strata gave +37% decode on code, but it lowered the agent score from 5.6 to 4.5/10 and produced loops ([Avalon upgrades][av]). Turbo-hip needs no more engineering work, only a **quality decision** (item 7). AcceptMoE (Imperial, item 23) refines it with a depth-graded prior that keeps position 0 exact (5–15% estimated). Activation sparsity on the CPU experts (the Berkeley intra-expert mask, TEAL, CATS, CHESS; item 13) has a 1.25× ceiling and a realistic gain of 10–20%, but it is lossy: the USA report notes −3.4 points at 85% sparsity ([USA P1/P2][us]; [MIT #1-2][mit]).

**The drop after long prompts** is an exact and well-localized loss. The prompt path borrows **9,412 cache slots (12.6 GiB)**, and decode falls from ~125 to **~105 tok/s** until the cache refills ([MOD_PLAN item 2][mp]; [profile-fasthip][prof]). No paper in the series covers it directly, and "VRAM lending" on the 3060 did not change decode. dan-cd's lend sweep is in the queue.

**The GPU floor** (15.9 ms, 64% of the short window) matters only on short chats. If every GPU component were 10% faster, the short window would drop by ~1.6 ms (~6%), and on edits the gain would be close to zero while the GPU waits for the CPU. The profile brings a **new finding, absent from items 1–37**: the down projection of the VRAM-resident experts runs on the default kernel, **`native_down_multi_kernel<42>`, with 5.79% of GPU kernel time** (4,224 calls, 37.6 µs each). The reason is that the "IQ2_XS" file has its down tensors in **Q2_0**, which the fast expdec path does not cover. The log says it explicitly: `strata expdec: CUDA0 down type 42 (n_embd 2560, n_ff 640) not covered: the default kernel runs` ([run_kernel_stats][ks]; [iq_kernels.cu:4155][iqk]; [Europe F3][eu]). An expdec-style down kernel for Q2_0 at n_ff 640 could cut a third of this share, i.e. ~0.3–0.6 ms on the short window (~1–2% decode on chat, ~0 on edits). FLUTE (MIT) and the UFMG sweep (Pacific R4) are the closest methods, but no report names this gap. Next to it sit Gated Residual small-M (item 32, part of the ~2.73 ms of hyper-connection reads) and the UFMG sweep (item 37). Each is worth 1–5% on short chat ([Asia P5][asia]; [Pacific R4][pac]; [MIT #13][mit]). The **feat/bitdecoding-hip** branch targets attention, which is only ~3% of decode: the opt-in WMMA kernel has an unconfirmed gain of ~2–3%.

**The draft** (2.2–2.5 ms, 6.7–9% of the window) has 71% acceptance on short chat, 94% on edits and only **55–66% after 11.7K prompts** ([pancake-flashnext.log][log]). MTP in the verify graph (item 10), `--mtp-q4` (queued) and DISCO/SpecFit/SuffixDecoding (items 15, 36; the **feat/disco** branch) promise 0–10% exact ([Asia P3][asia]; [Pacific R2/R3][pac]; [USA P8][us]). Even halved, the draft would bring only 3–5% on short chats.

## The turn tail comes from re-reads and thinking, not from tok/s

The agent side is dominated by a few long turns. **90.8% of turns hit the conversation cache**, and the median uncached input is only 226 tokens. Still, three kinds of re-reads add up to ~13M tokens, i.e. **~2 hours of prefill out of ~11.4 hours of turns** ([server_agent_ops][sao]). First: **207 turns in the same session re-read more than the prompt grew** (median 16.9K, p90 77K, 6.05M tokens, ~55 min at 1,850 tok/s). Second: **~103 switches between sub-agents or sessions** re-read ~5.5M tokens (~50 min). Third: **38 compaction requests** read 1.51M tokens, because opencode's compaction prompt shares no prefix with the conversation. The 18% estimate is a lower bound, since prefill at 64–120K is slower than the 11.7K rate used in the calculation, and the median prompt of these turns is 64.5K tokens.

Each category has its own technology, and the first step is shared: **the restore-equivalence test (UNSW, item 35)**. A full restore of a parked conversation must give exactly the same tokens as a cold recompute, with the off-by-one check on `cache_n`/`prompt_n`, because UNSW found exactly such a bug in a hybrid-state cache ([Pacific R1][pac]). The test gates items 3, 11, 16 and 31. Four levers follow it. Message-boundary checkpoints (`STRATA_CACHE_MESSAGE_BOUNDARY`, `--prompt-cache-tail`; item 11) gave, in the author's measurement on other hardware, **a first edit 33% faster** (17.24 → 11.53 s). Checkpoints at tool-call/tool-result boundaries with eviction by FLOPs saved per byte come from **Marconi** (Princeton/AWS, TTFT down to −71.1% on SWE-bench traces) and **FreeToken** (item 16) ([USA][us]). The third is end-to-end `preserve_thinking` (item 31): the template keeps `<think>` from previous turns, but if opencode does not resend `reasoning_content`, the prefix breaks on every turn. Nobody has checked this yet, and a single logged request would settle it. For switches between sub-agents there is the **RadixAttention multi-state store** (Stanford), the Continuum/MORI TTLs and a disk tier (llama.cpp #28092, phase 7) ([Stanford][stan]; [Avalon upgrades][av]). The current budget of **5.4–6.1 GiB for 4 parked conversations** holds only 2–3 long conversations, at ~1.1 GB per 51K-token snapshot ([pancake-flashnext.log][log]). Compaction cannot be fixed in the engine. Slipstream (async compaction in tool windows, −39.7% latency) and ACE (delta compaction) need changes in the harness ([USA][us]; [Stanford][stan]). **ContextPilot** (feat/contextpilot) measured only **1.6% savings** on 40 real sessions and should stay off ([MOD_PLAN][mp]).

**Thinking has no cap in daily use.** opencode sends `reasoningEffort: "xhigh"` by default. `reasoning_budget_by_effort` (5dd620fb9), `reasoning_budget_grace` (the Maya-style soft close) and `reasoning_close_retry` (#1053) exist in code, but they are opt-in and appear in no preset. The only one on by default is `answer_room` ([server_agent_ops][sao]). The 15 turns cut at the output cap took 84–340 s each. The literature supports a cap. With s1 budget forcing, accuracy saturates as the budget grows. The Berkeley study "Danger of Overthinking" shows ~30% better results and 43% less compute by picking the solution with less thinking, on 4,018 SWE-bench trajectories. "Are LRMs Interruptible?" finds up to 60% accuracy loss on abrupt cuts, hence the need for a soft close ([Stanford][stan]; [USA][us]). The reports admit, however, that **no paper evaluated effort levels on agentic coding turns**. So a "medium" default is a hypothesis that must pass the quality gates. A cap that only cuts the tail above p99 is a low-risk decision. As a reference, the p99 of reasoning text is ~17.9K characters, roughly 4–5K tokens as an estimate. Later, learned stopping (Thought Calibration, MIT: up to 60% fewer thinking tokens in distribution; item 21) and the 5-gram rumination signal (Thoughtology, Mila/McGill; item 34) can target 20–40% of the thinking in routine turns ([MIT][mit]; [Canada][can]).

**Turns are not observable.** `tokens.reasoning` is 0 in all 2,063 turns, because the server counts `thinking_n` but does not put it in the chat-completions usage (only in the Responses API). Also, the metrics live only in memory. Without `completion_tokens_details.reasoning_tokens` and a per-turn JSONL log, no A/B for items 11, 16, 31 or 12 can be read from real sessions. This is plumbing, not research.

**Tool-call reliability is already good**: 22 errors in 2,362 calls (0.9%), 23 "invalid" calls and **a single `oldString not found` in 180 edits**. Grammar in speculative decoding, tolerant recovery and the conversion of late system messages are already active. Item 26 (the ETH type-constrained decoding on `oldString`) has almost nothing to fix ([Europe][eu]). The remaining errors come from tool-set mismatches (9 `caveman_retrieve` "unavailable" calls), i.e. from the harness configuration. The real gap is behavioural: failed runs cost 39–343% more tokens (UBC/Queen's), and the loop guard catches only lexical repetition. The item 33 counters (log only at first) and ECLoop (read-before-edit, test-before-done, +4.8..+11.8 pp) cover this gap ([Canada][can]).

## Operations are the weakest link, and no paper covers them

**Pancake has no service unit.** `strata.service` runs the old checkout `/home/dan/Strata` on port 11437, `avalon.service` uses the same port, and `run-pancake.sh` starts on **8080** by default ([server_agent_ops][sao]). Since 2026-11-02 there have been only 2 local turns. No opencode session has run on pancake. On the client side, the `strata-coder` sub-agent asks for `strata/qwen3.6-35b-a3b` with a 163,840 context. Pancake answers any unknown name with its own model, whose maximum is **131,072**, so a sub-agent request above that limit will hit the context check. The 19–41K tokens of system prompt in the oh-my-openagent agents (unpinned version) multiply cold reads on a single-slot server. Each agent has a different system text before the tool schemas, so there is probably no shared prefix today.

**A restart costs 28–65 s just to read the 33.02 GiB arena** from the ntfs3 partition (0.51–1.18 GiB/s over 13 starts). The 2.3× variation on identical files points to page-cache state and concurrent I/O, not to the engine. On top of that come ~10 s of setup, plus up to 10 minutes while `capped.sh` waits for 48 GiB free. A restart also loses all parked conversations, which live only in RAM ([pancake-flashnext.log][log]; [capped.sh][capped]). Building the arena often triggers systemd-oomd. The alternative `STRATA_RAM_KEEP_GIB=20` (mmap tier) starts every time, but decodes ~8% slower. This decision also fixes the parked-conversation budget, so it must be made together with the sub-agent switch data. For loading, the research offers only indirect pieces: `MADV_SEQUENTIAL` (upstream, later turns went from 65–76 s to 23–28 s on an RX 6900 XT with 32 GB), disk sessions (FastStrata `--conversation-disk`: a 70K conversation resumed after a restart in **7.2 s instead of 83 s**) and basalt's sleep-in-place ([Avalon upgrades][av]; [MOD_PLAN phase 7][mp]). Hugepages would need 16,920 pages of 2 MiB (`vm.nr_hugepages=0` now). It is a system setting that has not been measured and that only the owner can make.

**The build has two concrete problems.** The first is the link failure with `STRATA_PREFILL_MMQ=OFF`. engine.md found no trace of it in the `build-hip` logs, but those are MMQ=ON builds, and the static check of the stubs missed the cause. Two separate agents hit the error when compiling with MMQ=OFF. The cause is that the fused stub block in [src/prefill/prefill.cpp][prefill], used when `STRATA_PREFILL_FUSED` is not defined (i.e. MMQ off), does not contain `want_dm_f16()`/`dm_f16_used()`, added by commit `6e31946cb`. **A 2-line fix in the stub awaits verification after 13:35.** Even an OFF build that links would silently lose fast-hip's fused int8 prompt experts. The second problem: `strata-poly` is declared for HIP in CMake, but `run-pancake.sh` refuses it as "CUDA-only". Several switches in the preset do nothing on this build (`STRATA_SELECT_LONG`, `STRATA_PF_GROUP_SCRATCH`) ([engine][eng]).

**Correction about BFLA.** server_agent_ops.md treats it as a mismatch that the port on **feat/bfla-hip** touches `src/qwen35/q36_engine.cu`, but the choice is intentional. The port targets the qwen35 engine, which the main `strata` binary uses for the Qwen3.6/3.8-35B GGUFs and which compiles on HIP. On Flash-Next, pancake's prompt path already runs **sparse QSA (2,051 cells per query)**. The BFLA budget, of up to 32K cells, would be slower, and the QSA baseline in the BFLA paper itself is as fast or faster ([Asia P9][asia]; item 19). The only BFLA lever for Flash-Next is **a single shared QSA selection over a tile of queries**. It would be lossy and opt-in, and the overlap must first be measured with `STRATA_SEL_OVERLAP`. The prototype is in progress.

**The documentation has drifted from the code.** The model appears as "125B MoE" in the README, but the Europe report gives 176.9B with the n-gram table. The file named "IQ2_XS" actually has IQ2_S/IQ2_XXS/IQ1_M experts with Q2_0 down. `run-pancake.sh` uses iq2_xs by default, although MOD_PLAN states "Q2_0 is the daily file". And `strata-iq2_xs.json` in the repo root still points to CUDA libraries. The test `test_keepawake.py:80` fails both on the base and on the branch. The tested function is Windows-only, so it does not affect Linux, but it blocks an A/B gate that needs a "green suite".

## The gaps no research covers

The hardest limits are physical or environmental. **DDR4 bandwidth** for the CPU experts has a single lever, DDR4-3600/FCLK 1800, for the owner to decide, and unmeasured. **PCIe 3.0** (13.4 GB/s, promotion ~115 µs against ~42 µs of CPU compute) explains why `--pcie-frac 0` wins. **The 20 GB of VRAM** keeps only 44% of the expert pairs resident, and the fix would be a second GPU (phase 12). The Asia report says it plainly: no paper evaluates PCIe 3.0, AMD GPUs, 512 experts per layer or a GDN hybrid with misses computed on the CPU ([Asia][asia]). Next to these sit **load speed from ntfs3** (file system choice, hugepages), **the tight root disk** and **the noise of a shared machine**.

Some gaps are not physical, but the series still does not cover them. The first is **determinism**: the GPU rounds differently from the CPU, and the adaptive tier moves experts, hence the 1.17–1.30% mismatch between two stock runs. The second is **the ~20% run-to-run variance**, which means an exact 1–5% item (29, 32, 37, the Q2_0 down kernel) cannot be accepted from 2–3 runs. The third is **the fixed per-turn overhead of ~0.5–0.9 s**, which stays unexplained after the read time went down. On the agent side there are also: service/port/lifecycle integration, `reasoning_tokens` in usage and the per-turn log, prompt reordering (tools first, then the agent text) for a shared prefix between sub-agents, matching opencode's limits to the server, a RAM policy that splits memory between the arena and parked conversations, a cold-start shortcut beyond sleep-in-place, and pinning the oh-my-openagent version with an audit of the tool set. The Q2_0 down kernel is also our own kernel work: FLUTE and UFMG are only methods. All of this is ordinary engineering and needs no research.

## One work order, from configuration to the lossy levers

The two rankings answer different questions. engine.md orders by milliseconds per window times the chance of success, so it puts CPU experts on edits first. server_agent_ops.md orders by user-visible time and puts wiring pancake, the thinking caps and the re-reads first. Both are right in their own unit, but their order is not symmetric. **No engine gain reaches the user while pancake does not serve opencode**, and **no per-turn lever can be validated without the per-turn log**. So the first two rows are preconditions, not competing priorities. On the other hand, the engine work in dan-cd's queue can run in parallel, because it does not overlap with the research session. The lossy levers come last regardless of size: even the biggest measured gain of the series, turbo-hip, has a documented counterexample (upstream agent score 5.6 → 4.5) and must pass the revised gates (token forcing for large deviations, then the fixed set: LiveCodeBench subset, BFCL v4 multi-turn, checkpoints from our own repo, repeated runs) ([MOD_PLAN][mp]; [Canada][can]).

## Conclusion

The analysis changes the question from "how do we make tokens faster" to "how do we make turns shorter". A 20% decode gain shortens a 6 s median turn by at most one second. By contrast, a single runaway turn or a sub-agent switch with 60K re-read tokens costs tens of seconds to minutes, and both already have levers in code that only wait to be enabled and verified. The engine stays important for edits, where CPU experts make up almost half of the window, but the physics of DDR4 and PCIe 3.0 leaves only three strategies there: fewer bytes, bytes hidden by overlap, or routing that avoids the bytes. The last one is the biggest and the riskiest.

All the agent numbers in this report come from an old backend. The first thing pancake can produce once wired to opencode is its own per-turn timeline. That will show whether the ~18% re-reads and the thinking tail hold on this engine too, or whether the fixed ~0.5–0.9 s overhead and the drop after long prompts are actually the dominant problem. Until then, the order above is a well-founded hypothesis, not a certainty.
