# Isolate the combine spin before rewriting window sync

The per-window overhead on the RX 7900 XT is mostly **host-pool latency that the GPU stream waits on**, not launch cost, so no fusion switch can remove it. The largest single term is `combine_cpu_k10_vec4<true>` at **670.6 ms, 18.9% of the 3553 ms decode wall** [profile], but the profile cannot say how much of it is spin rather than arithmetic [unverified]. The two wait kernels add **293 ms (8.3% of wall)** [profile], and fusing their copy into the wait removes at most about **10 ms (0.3%)** of graph-node cost [derived]. The owner should therefore test in this order: (1) record the profiled process's full environment and split the combine time with one poll-off A/B; (2) run the cheap exact Speed switches that were never isolated (WAIT_FUSE, FUSE_WAIT, spec depth); (3) only then touch code that moves the host waits (pool latency, window-end sync, device-side waits). The lossy deferral family was already measured and gave no clean win, so it is last. Nothing in the literature measures this overhead on a single RDNA card, and every paper cited below was read from its abstract or a search excerpt.

## What the profile shows and what it does not

The profile confirms the headline numbers: **decode 3553 ms, kernels 2712 ms (76%), 470 kernels per token, 699 ms of launch gaps under 50 us, and 93 ms of host stalls above 1 ms** [profile](/home/dan/profile-pancake-2026-11-12/summary.txt). The wait kernels are spin time. `wait_flag_ge_kernel` ran **288 times for 150.1 ms**, with a median of 11.2 us but a mean of 521 us, and 136 calls above 100 us account for almost all of it [profile, audit](/home/dan/research_notes/Speculative%20window%20overhead%20reduction/pancake_window_audit.md). The code confirms the mechanism: the kernel spins on a mapped host flag, then issues `__threadfence_system` [code: verify_kernels.cu:1330-1333]. `wait_flag_copy_i32_kernel` ran **4320 times for 143.1 ms**, and its thread 0 spins before every block copies from a mapped host pointer [code: verify_kernels.cu:1396-1407]. Together they are a latency problem: the GPU is idle-waiting on the CPU expert pool, and fusing the copy removes one node per plan but leaves the spin unchanged [derived].

The combine kernel is the largest term and the least understood. The profile ranks it first at 670.6 ms over 4032 calls, with 1823 calls above 100 us [profile]. The code explains why part of it is spin: with `STRATA_WAIT_FUSE` on, `poll_slot < 0` makes every combine block's thread 0 poll the PCIe-mapped flag, and `poll_slot_of` returns -1 unless `STRATA_COMBINE_POLL1=1` [code: native_moe.cu:166-172, 267-269]. The profile cannot separate that spin from the arithmetic inside the same kernel [derived]. Until it is split, the 18.9% figure is a ceiling, not an opportunity.

The copy after `mtp_select` needs a correction to the assignment's framing. The 17.5 ms total is real and comes from 48 pairs [profile], but its median gap is only 106 us and **three outliers (1893, 4639 and 5824 us) account for about 12.4 ms of it** [audit]. "Mostly host turnaround" is therefore an inference from timing, not a measurement, and the outliers point to host preemption or a pool wait outside the GPU [unverified]. The profile also shows a second, unexamined pair: `__amd_rocclr_copyBuffer -> copy_i32_from_mapped_kernel` at **16.9 ms over 83 gaps** [profile]. The audit does not cover it. Together the two pairs are 34.4 ms, about 1.0% of decode [derived]. The `kv_append_q8 -> copyBuffer` gap of 57.7 ms is a single 57 ms outlier and is not per-window cost [profile].

Three corrections to the notes apply. `src/program/generate.cpp` has no `wait_flag`, `copy_i32_from_mapped` or `mtp_select` call sites, only the `set_commit_async` policy call at line 6027 [code, audit]. The real sites are `src/core/verify.cpp` and `src/core/mtp.cpp`. `include/strata/spec/` holds policy only and launches no kernels [audit]. Finally, the profile directory records CLI flags but no `STRATA_*` environment [profile], so the state of WAIT_FUSE, COMBINE_POLL1 and VERIFY_DEVICE_PLAN in the profiled process is unknown [unverified]. Every switch-level conclusion below depends on that gap, which is why it heads the test order.

## Which switches were tested and which were not

The keyword scan of `conversation_disk_env.def` found 153 candidate switches, and only about 20 have an A/B arm in a result file [measured, notes](/home/dan/research_notes/Speculative%20window%20overhead%20reduction/untested_switches.md). The measured ones that matter here are narrow. **EXPDEC_DOWN** gave **+1.7% ±0.5** on the short decode, with an edit arm at +5.4% ±7.3 that was not significant [measured, test-phase 04c]. **MTP_EAGER** gave +1.6% ±5.2, not significant, and stays opt-in [measured]. **POOL_FUSE_PHASES** gave +2.5% ±1.7 on the edit arm [measured]. **VERIFY_DEFER_AUTO** was worse than always-on deferral, by **-1.2% to -12.5%** [measured, night queue defer-iq2xs-03C], and should not be retested. The rank-guard family (DEFER_CPU_TOP, DEFER_CPU_FOLD) was flat or negative on edit (top2 at -4.2% in recomputed row means) [measured].

The switches with no isolated result are the ones that matter for the wait path. **WAIT_FUSE** is a Speed switch that is on in the preset env dumps but has no A/B arm, and its planned "judged on host CPU time" test was never found [coded only]. Its one estimate, 0-3%, comes from a design note [unverified]. A separate document lists it as a suspect for non-finite logits [code/notes, Grouped technologies line 234], so it needs a finite-logit check. **FUSE_WAIT** is gated on gfx1100 and has no result [coded only]. **WAIT_COPY256** and **ROUTE_FAST** each have one noisy pass: +6.8% at n=2 and +8.0% at n=4, against a base with a 95.9 tok/s outlier [measured, inconclusive]. **ROUTE_PUBLISH** is a correctness topic first; it was forced off under deferral after a non-finite-logit bisect [measured/notes], so it is not a speed candidate yet. **ROUTER_FUSE** was a screen only, +0.4 to +4.3% and not significant [measured].

## Literature: exact routes, lossy routes, and what was only abstract-read

The largest reported wall-time gains come from restructuring the draft-verify dependency, not from removing one sync. **Mirror-SD** reports **2.8x-5.8x** wall-time on SpecBench, averaging **30% over EAGLE3** [paper, arXiv:2510.13161](https://arxiv.org/abs/2510.13161). Its exactness is not stated in the abstract. **AMUSD** decouples draft and verify into asynchronous processes with a shared buffer and rollback flag, and reports an average **29%** gain with identical output quality [paper, arXiv:2410.17375](https://arxiv.org/abs/2410.17375), taken from a search excerpt. **PipeSpec** reports **2.25 vs 1.5 tokens per unit time** for a hierarchical pipeline with optimistic downstream assumptions [paper, arXiv:2505.01572](https://arxiv.org/html/2505.01572v1), from an excerpt. **Speculative Aggregation** claims equivalence to synchronous decoding [paper, arXiv:2504.11197](https://arxiv.org/html/2504.11197v2), from an excerpt. All four need a second draft model or early-exit signal and rollback on reject, so they change the dataflow and are not single-switch changes on Pancake [derived].

**SonicSampler** fuses sampling and speculative verification into one batched kernel and reports up to 10x for top-k and up to 16x over baselines [paper, arXiv:2607.20475](https://arxiv.org/abs/2607.20475). Its baselines and exactness are not in the abstract, and its gains are for sampling, not window latency. On Pancake's greedy path the host head sync at `verify.cpp:4228/4234` runs only for sampled requests [code, audit], so a fused sampler is worth little on this profile [derived]. A consumer-hardware paper on Apple silicon reports a best **1.61x** and says **three of five configurations slowed down**, because draft overhead can exceed a small target's decode step [paper, arXiv:2607.17283](https://arxiv.org/abs/2607.17283). That is the closest evidence that overhead can erase the gain on small-batch consumer hardware. Its distribution check (chi-square 162.5, p = 0.976) supports exactness for the tested configs.

On the device side, the CUDA driver API provides **stream memory operations** (`cuStreamWaitValue32` and `cuStreamWriteValue32`) so queued work blocks on a memory location without the CPU thread blocking, with batching to reduce overhead, and it warns of deadlock on misuse [paper/doc, CUDA driver API](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__MEMOP.html). No source found applies this to speculative decoding, and the HIP equivalent `hipStreamWaitValue32` was not checked [unverified]. A device-side wait would replace the spin kernels but keep the same host dependency, so it removes launch and occupancy cost, not pool latency [derived]. For the exactness question, greedy verify and standard rejection sampling are exact by construction, but a fused kernel can change argmax ties through reduction order [derived]. No source reports bit-exact equality for a fused verify against the reference, so each candidate needs a token-equality check [unverified]. The llama.cpp Vulkan issue on a shared Radeon iGPU, where cross-model waits drove draft throughput from 33-35 tok/s to 3-5 tok/s, is a cautionary case for waits on one device [unverified reporter hypothesis, [issue #23126](https://github.com/ggml-org/llama.cpp/issues/23126)].

## Conclusion

The per-window overhead on this card is a **latency problem on the host side of the flag**, and the profile shows that clearly. Fusing kernels, moving copies, or switching to a device-side wait each remove a node or a launch, which is worth at most a few tenths of a percent each. The levers that could matter are the ones that shorten the wait itself: the combine spin (up to 18.9% of wall, split unknown), the pool's flag latency (up to 8.3%), and the window-end host sync (up to 2.6%). Only the first of these has a clean exact A/B that the owner can run tonight, and it should be run before any code moves.

The notes also change how the earlier results should be read. Several "never measured" statements in the plan are stale, because EXPDEC_DOWN, DEFER_AUTO and ROUTER_FUSE have results. Deferral has been measured as lossy and mixed, so the owner should not spend window time on it again until the profile shows the 288 waits remain with deferral on. The literature supports the direction (restructure the draft-verify dependency) but not a single-switch gain on a single RDNA card, and no paper measures this overhead on gfx1100. The first night's work is therefore measurement: fix the environment, split the combine, then run the exact Speed arms in the order above.
