# The last round confirms the map: little fits

From Australia/New Zealand, Africa and Latin America (November 2022 - November 2026), **only one paper touches pancake's critical path: SpecFit** (Beihang lead, Monash co-authors). It shows that, with offloaded experts, each draft token has a different cost, depending on how many *new* experts it pulls into verification ([arXiv 2610.15417](https://arxiv.org/abs/2610.15417)). Pancake already has the coarse version of the idea: `DraftPolicy` prices each window width from measured times, and DISCO on `feat/disco` has a `miss_` feature, a moving average of misses per row. What is missing is the marginal cost *per position*, and that is worth at most a few percent at decode. The rest is peripheral, but cheap: a regression test for restoring hybrid state from the cache (UNSW), an offline coordinate-descent sweep of the HIP launch parameters and the AVX2 blocks (UFMG), top-k entropy as a signal for the loop guard and DISCO (UBA), and calibration on opencode traces, valid only at a requantization (AIMS/UCT). **No paper from the three regions covers CPU expert offload, MTP, GDN or ROCm**, and compressed KV (OSCAR, ZipCache, MiniCache) repeats the null result already measured with TurboQuant. The conclusion "little fits" is therefore a result, not a lack of effort. The report ends with the single ranking of the ~10 actions from the whole series of seven reports.

## How I read the papers: the same grid as in the previous reports

The grid is the one from the previous series. The decode window is **~24.8 ms, of which the GPU works ~15.9 ms**, and the rest is set by the missed experts, computed on the CPU (MOD_PLAN, item 1). A paper counts only if it shortens CPU time, reduces promotions over PCIe 3.0, picks the MTP window length better, or cuts tokens and turns of the opencode agent. The notes filtered by affiliation (OpenAlex `country_code` and institution IDs), then read the arXiv metadata and abstracts. Two limits matter. Many 26xx IDs are checked only through metadata, without the PDF. The second pass for Latin America (serving, early exit, structured output) hit the OpenAlex daily limit. "Nothing found" in Mexico, Chile, Colombia or at Makerere and Nairobi is therefore weak evidence of absence. The gains below are my estimates, not measurements, and the authors never used AMD, ROCm, PCIe 3.0 or a MoE with 512 experts.

## Australia and New Zealand: SpecFit and a correctness test

AU/NZ output on this topic is thin: many papers on vision, multi-agent and edge, very few on single-GPU MoE decoding. **SpecFit** is the only one with real impact. With offloaded experts, a larger draft tree means more transfers, and speculative decoding can even end up slower than autoregressive decoding. SpecFit picks the verified subtree that maximizes predicted throughput, not acceptance length. The cycle cost is computed from the *union* of the experts activated per layer, a submodular coverage function, so each node pays only for the experts it adds. On Qwen3-30B-A3B, the gain is **21.6% and 7.0% over EAGLE-3 with the same expert cache** ([arXiv 2610.15417](https://arxiv.org/abs/2610.15417)). Pancake drafts chains, not trees, so the search reduces to choosing T. The authors' figure is an upper bound, because `DraftPolicy` already measures cost per width (the comment in `src/spec/draft_policy.cpp` notes "+10 ms per token with every missed expert"). The key unknown is whether the union of experts can be predicted *before* verification. The abstract does not say how, and the answer must be looked for in the code ([github.com/Chlience/SpecFit](https://github.com/Chlience/SpecFit)).

The second useful contribution is about correctness, not speed. The UNSW report on GLM-5.3-Flash on vLLM/LMCache describes exactly the class of bug that threatens a cache with GDN checkpoints: on a full hit, the state was restored for the whole prompt, but the scheduler credited one token fewer. After the fix (strict prefix lookup and matching checkpoint scheduling), agreement with recomputation rose **from 34/36 to 36/36 generations** ([arXiv 2609.15030](https://arxiv.org/abs/2609.15030)). My search in `tests/` and `serve/` found tests with fake engines (for example `serve/test_ds4_restore_points.py`, for DeepSeek), but no GPU test that compares the Qwen restore with cold recomputation token by token.

## Africa: a calibration guide and unreviewed agent tools

Africa contributes nothing on the kernel or offload path. The region's LLM output is dominated by data, benchmarks and models for low-resource languages. The only paper that touches the inference stack is **Calibrating Beyond English** (AIMS/UCT lead, EACL 2026). Non-English and multilingual calibration consistently beats English-only calibration for GPTQ/AWQ, with **perplexity lower by up to 3.52 points** on Llama-3.1-8B and Qwen2.5-7B, and matching the calibration language to the evaluation language gives the largest gains ([arXiv 2601.18306](https://arxiv.org/abs/2601.18306)). The lesson for us is domain alignment: at a requantization, the calibration set should come from opencode traces (code, tool-call JSON, thinking, chat in Romanian and English). The paper, however, tested 4 bits on dense 7-8B models. The idea that the effect grows at 2 bits is an inference, and for the daily Q2_0, already quantized by ISTA-DASLab, nothing changes.

The KNUST group (Agyemang, Kponyo) published a series of tools for coding agents in 2026, all on arXiv and with benchmarks built by the authors. **Resilient Write** is an MCP server for durable writes (atomic transactions, resumable chunking, typed errors), with **5x faster recovery** than the authors' baselines ([arXiv 2604.10842](https://arxiv.org/abs/2604.10842)). **Cartograph** cuts tool definitions in context from O(n) to O(k): **475 tokens instead of 42,450** for 374 tools ([arXiv 2609.30293](https://arxiv.org/abs/2609.30293)). With the rea MCP disabled and a small tool set, though, the gain would be almost zero for us. **Entropy Gate** compresses the prompt lossily and deduplicates repeated blocks ([arXiv 2606.03739](https://arxiv.org/abs/2606.03739)). The dedup overlaps with `feat/contextpilot`, which measured only **1.6% savings** on real opencode sessions, and deleting tokens breaks the exact-prefix hits of the conversation cache. Both are arguments for leaving them off.

## Latin America: an autotuning recipe and free signals from logits

Latin America has a little more systems content. **UFMG** (Quintão Pereira) shows that Ansor's exploration can be capped at ~300 kernels, followed by exploiting the best one with coordinate descent. The result is "usually" better and faster than search with 10,000 samples, replicated on 20 models, including on an **AMD Ryzen 7**, and the patch was merged into Ansor ([arXiv 2406.20037](https://arxiv.org/abs/2406.20037)). The 2026 sister paper gives the most relevant figure: **5.5-8.5% from tuning thread-block sizes alone** on an A100 ([arXiv 2609.03114](https://arxiv.org/abs/2609.03114)). The framework does not transfer, because pancake's kernels are hand-written HIP. The method does transfer: an offline sweep over the hot kernels that the item 1 profile shows. With the GPU at ~64% of the window and the kernels already hand-tuned, this means **at most 1-3% end to end** (my estimate).

**UBA** (Del Corro) brings the most useful line for the agent side. **Entropy Sentinel** compresses a response's top-k entropy profile into a small vector, from which a light classifier predicts quality. Correlation with LLM-judge scores reaches **r = 0.91** for some models, not for all ([arXiv 2601.09001](https://arxiv.org/abs/2601.09001)). Pancake already computes logits, so the entropy is practically free. DISCO today uses `p` and `-log p` of the chosen token, not the entropy of the distribution, and the Asia report had already asked for the entropy feature. **A BERTology View** trains small probes on hidden states from the same forward pass, validated on MoE backbones such as Qwen3-30B-A3B ([arXiv 2601.13288](https://arxiv.org/abs/2601.13288)). The same infrastructure serves the item 21 probe and could predict a malformed tool call before it is decoded, but this stays R&D. The rest (LP-GEMM, MoP, PRISM) does not apply at batch 1 or to a MoE already at 2 bits.

## Closing the series: ten actions, in a single order

The ranking below combines the plans from the seven reports: [Stanford](../stanford/report.md), [MIT/Harvard](../mit-harvard/report.md), [rest of the US](../us-universities/report.md), [Europe](../europe/report.md), [Asia](../asia/report.md), [Canada](../canada/report.md) and this report. The ordering rule: first what drives other decisions or is already nearly done, then exact gains before lossy ones at an equal ceiling, then the agent. The precondition for all of them is the **revised quality gates**: token forcing only rejects large deviations, and between close variants a fixed task set decides (LiveCodeBench + BFCL v4 multi-turn + tasks from our own repositories), with repeated runs (Canada-M1, US-M2/M4).

## Conclusion

The last round moves nothing in the ranking, and that is its main information. The papers that matter for a machine with a single consumer GPU, DDR4 and experts on the CPU come from a few labs (Berkeley, CMU, ISTA, Imperial, Tsinghua, SJTU, plus the Qwen report). The rest of the world publishes on multi-tenant serving, compressed KV and dense models, that is, problems pancake does not have. SpecFit is the exception that confirms the direction: the cost of a draft token is the cost of the new experts it wakes up, exactly the principle already in `DraftPolicy`, now refined from width to position.

The second lesson is about the nature of the remaining gains. After seven reports, no paper promises a jump like the 87 → 112 tok/s obtained from the RDNA3 ports. What remains are decisions (turbo, item 7), fixes (item 8), a measurement that may open 10-20% (item 13), and a lot of agent time lost in thinking and re-prefill. That is why the restore equivalence test, cheap and with no speed gain, sits in the ranking next to kernels: every cache optimization in places 4-5 rests on it.
