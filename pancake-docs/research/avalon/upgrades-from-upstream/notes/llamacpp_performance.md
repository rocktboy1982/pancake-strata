# Upstream llama.cpp performance PRs relevant to Avalon on an RX 7900 XT (gfx1100, ROCm 10) running Qwen3.8-Flash-Next with experts offloaded

Scope and method: as of 2026-11-08 I used `gh` to search open and merged PRs in ggml-org/llama.cpp (merged since 2026-09-01), plus open issues and Discussions. Each item gives its number/URL, title, status and date, what it does, the speedup the author claims (with their hardware), whether it applies to HIP/gfx1100, and risk. All speedup numbers are the authors' own claims from PR threads. None were reproduced here.

Context on Avalon (checked locally, read-only): `/home/dan/clone-of-d/Avalon` is at commit a91372e, which reports llama.cpp version 0.8.0. Upstream bumped to 0.8.0 on 2026-10-28 ([#31309](https://github.com/ggml-org/llama.cpp/pull/31309)). The history is squashed (5 commits), so no merge-base can be found. Avalon has its **own** MoE cache API (`llama_moe_cache_mode`, `moe_cache_budget_mib`, `moe_cache_expert_parallel` in `include/llama.h`). It does **not** have upstream's `--moe-cache-mib`, `--moe-cache-cpu-share`, `--spec-draft-n-ubatch`, `draft-mtp-adaptive` or `--moe-direct-io` flags (grep of `common/`, `src/`, `tools/`). It does have its own QSA attention for q8_0/q4_0 K/V by tile lists (commits 2c346ba, d66513f). So any upstream feature below has to be ported or cherry-picked by hand. It will not arrive with a plain rebase.

## Which open/recent PRs improve HIP/ROCm kernels for RDNA3 (MMQ, MMVQ, flash attention, rocWMMA, MoE/mul_mat_id, fused ops)?

### Takeaway
The highest-value RDNA3 items are three. #31751 (open, draft) removes J=32 MMQ register spills on gfx1100 and gives +36% at 17-32-token batches, which is exactly the MTP/n-gram verify size. #31234 (open) adds native q4_0/q8_0 KV in the HIP flash-attention tile kernel, with up to +24% decode at 131k context on RDNA4/ROCm 10.1. #31746 (open, draft) tunes D256 MMA flash attention on gfx1100 for 16-30% lower attention-op time. Several merged CUDA-side MoE fusions (#29948/#31188 gate/up+GLU in MMQ, #31047 linearized MoE layout) also compile into the HIP backend, but they were benchmarked only on NVIDIA. One of them regressed gfx906.

### Inferences
- #31751 is the most directly applicable kernel PR. MTP + n-gram verify batches are typically 2-30 tokens, which is the PP17-PP32 range where +36% was measured on gfx1100. It is a tiny change (one pragma), so it is a cheap cherry-pick if Avalon's weights use one of the Q8_0-layout types (Q4_0, IQ4_NL, IQ4_XS, MXFP4, Q8_0 ...). It would not help K-quants.
- #31234 (or #30792) fits Avalon's q4_0/q8_0 KV at 131k context, where the gain is largest (+13-24% at 64-131k). Avalon already has its own QSA tile-list attention with q8_0/q4_0 gather, so the overlap must be checked before porting.
- #31746 only affects D=256 attention layers at large batch (prefill or verify). Whether Qwen3.8-Flash-Next's full-attention layers are D=256 and which GQA ratio they use needs checking against the GGUF.
- The merged fused gate/up+GLU MMQ path (#29948/#31188) should be A/B tested on gfx1100 before adopting, given the gfx906 regression report.

### Gaps
- None of the RDNA3 PRs were measured on Qwen3.8-Flash-Next itself or with experts offloaded. The quant type of the Avalon GGUF (which determines whether #31751 applies) was not checked.
- No PR shows HIP numbers for #31802, #30489 or #29948/#31188 on RDNA3.
- I found no open PR that restores a rocWMMA path. The rocWMMA FA kernel was removed upstream; #26419 and #31746 are the WMMA replacements.

## Which PRs improve MoE expert offload performance (CPU+GPU hybrid, `--n-cpu-moe`/override-tensor, expert prefetch/caching, mmap/NVMe streaming)?

### Takeaway
Since early October upstream has had a merged **GPU-side MoE expert cache** (`--moe-cache-mib`, #29887). It was benchmarked on this exact model, Qwen3.8-Flash-Next, with **1.57-2.2x decode** on RTX 4090/5090, and it runs on HIP (R9700: 1.3-2.5x). It was quickly extended with SLRU, then ClassLRU eviction (+6% decode on QFN), and "run misses on CPU" with a tuning script (`--moe-cache-cpu-share`, merged 2026-11-07). Out-of-core NVMe streaming for models bigger than RAM (our case) is still open RFC work: #31469 claims 1.5→16-22 t/s and #25294 is similar. A ROCm-specific mmap load-hang fix (#31886) is open.

### Cited Findings
**Merged**
- **#29887 "llama : add a GPU cache for MoE experts kept in host memory"**: MERGED 2026-10-07, am17an, a port of the qvac-fabric cache. MUL_MAT_ID on host experts runs on the GPU from an LRU cache, and only misses are uploaded. It applies to batches ≤32 tokens only. Bigger batches use the regular offload path. Enabled with `--moe-cache-mib N`; about 10% of expert size is the suggested starting point. Claimed on **Qwen3.8-Flash-Next Q4_0 (93.7 GiB, 65.4 GiB experts)**, EPYC 7742, PCIe 4.0 x16, no MTP: RTX 4090 25.0 → **39.4 t/s (1.57x)** with `--fit --moe-cache-mib 6544`, and 40.7 (1.62x) with `-cmoe --moe-cache-mib 11000`. RTX 5090 30.8 → 54.5 (1.77x), and **67.8 (2.20x)** with `-cmoe --moe-cache-mib 19000` (89% hit rate). — [PR #29887](https://github.com/ggml-org/llama.cpp/pull/29887)
- HIP results for #29887 from a PR comment: R9700 (gfx1201), Windows, HIP 7.1, Qwen3.8-Flash-Next IQ1_M (24 GB of experts), `-cmoe`. Decode went 11.0 → 14.5 t/s at 8000 MiB (1.3x) and 27.6 t/s at 16000 MiB (2.5x), with decode hit rates of 85-95%. That box had host experts mmapped from a 55 GB buffer on 32 GB RAM. The commenter notes that misses are uploaded straight from mmapped pageable memory, which HIP stages or registers per copy, and that Strata uses a pinned staging buffer instead. — [PR #29887 comment](https://github.com/ggml-org/llama.cpp/pull/29887)
- Counter-evidence in the same thread: a GLM-5.3-Flash test on 2x RTX 5090 over PCIe 4 found the cache made decode **slower** than no cache, and the "10%" rule did not carry over. — [PR #29887 comments](https://github.com/ggml-org/llama.cpp/pull/29887)

- **#28055 "llama-mmap: don't use MAP_POPULATE on Linux"** (OPEN, 2026-08-30) and **#29195 "mmap-on-demand"** (OPEN, 2026-09-21) avoid the blocking full-model read at start, which affects startup for models bigger than RAM. — [PR #28055](https://github.com/ggml-org/llama.cpp/pull/28055), [PR #29195](https://github.com/ggml-org/llama.cpp/pull/29195)
- **#31886 "rocm: fix mmap model loading hang with staged uploads"**: OPEN, 2026-11-08. On ROCm, passing mmapped pointers to `hipMemcpyAsync` accumulates userptr registrations until "amdgpu: SVM mapping failed, exceeds resident system memory limit", and loading then hangs. The fix stages through a ≤64 MiB double-buffered pinned buffer. Related: Issue #29149 reports that Qwen3.8-Flash-Next livelocks during load on HIP while the same config works on Vulkan. — [PR #31886](https://github.com/ggml-org/llama.cpp/pull/31886), [Issue #29149](https://github.com/ggml-org/llama.cpp/issues/29149)
- **#31139 "Add max allocation size reporting and split MoE cache groups"**: OPEN, 2026-10-25. Splits oversized cache banks; Vulkan only reports the limit. — [PR #31139](https://github.com/ggml-org/llama.cpp/pull/31139)
- Open bug: `--moe-cache-mib` aborts at load in `llama_moe_cache::impl::copy` on ROCm/HIP (RX 6800 XT gfx1030, b12110), independent of cache size. — [Issue #31675](https://github.com/ggml-org/llama.cpp/issues/31675)
- Issue #25859 profiles single-GPU `-ncmoe` prefill on an RTX 3060/PCIe 4: the GPU sits idle on serial expert H2D copies. — [Issue #25859](https://github.com/ggml-org/llama.cpp/issues/25859). Feature Request #29949 asks for cache decisions and copies to run on the GPU inside the graph, with no per-step id readback. — [Issue #29949](https://github.com/ggml-org/llama.cpp/issues/29949). RFC #31876 (BigMoeOnEdge) proposes automatic VRAM/RAM/flash placement for models bigger than memory, supporting ROCm. — [Discussion #31876](https://github.com/ggml-org/llama.cpp/discussions/31876)

### Inferences
- Avalon already has its own MoE cache, so the useful upstream pieces are the policy improvements: ClassLRU/CRF eviction (#31233, +6-7% on QFN), CRF-based CPU-miss selection (#31853), the "run misses on CPU" share (#30966) and its tuner. These are worth comparing against Avalon's eviction policy and CPU fallback rather than adopting wholesale.
- Our model (~89 GiB) is bigger than RAM (~57 GB), so every miss can also be a page fault from NVMe. #31469's victim cache, O_DIRECT pager and no page-cache duplication, plus #26414's hot-expert mlock, target exactly this regime. Both are open, unmerged and NVIDIA-tested, so they carry high porting risk.
- #31886 (pinned staging for HIP uploads from mmap) is relevant to Avalon's ROCm load path and possibly to MoE-cache miss uploads from mmap. The R9700 commenter raised this same pageable-memory concern for #29887.
- #30594 is not a good fit: its hybrid mode explicitly does not help speculative/MTP verify batches.

### Gaps
- No upstream MoE-offload benchmark uses an RDNA3 card or a model bigger than system RAM on ROCm. The only HIP numbers are the R9700 comment, where RAM was also oversubscribed.
- I could not determine how Avalon's MoE cache compares with upstream's ClassLRU, because Avalon's history is squashed.

## Which PRs improve speculative decoding (MTP, n-gram, EAGLE, draft model, tree speculation) or prefill (batching, chunking)?

### Takeaway
For a GDN-hybrid model like Qwen3.8-Flash-Next with MTP, the open PRs that matter most attack per-round overhead. #28118 keeps recurrent-state spec checkpoints on-device: on gfx1151 the host round-trip was 600 of 825 ms per round, and fixing it took spec decoding from 6.2 to 41-57 t/s. #31669 replays GDN instead of rolling back snapshots. #31750 adds KV-only MTP catch-up graphs (about -2% per step). Adaptive MTP depth (#27210) and drafting all tokens in one decode (#27173) target better depth use. Merged: probabilistic drafting with rejection sampling (#27694), saving/restoring the MTP hidden state (#30141), and `--spec-draft-n-ubatch` (#30459).

### Cited Findings
- **#28118 "server : keep speculative recurrent-state checkpoints on-device"**: OPEN DRAFT, 2026-08-31. For GDN/Mamba hybrids (Qwen3-Next/qwen4exp) the server snapshots the full recurrent state every spec round with `PARTIAL_ONLY`, which serializes to host. The PR ORs in `LLAMA_STATE_SEQ_FLAGS_ON_DEVICE` at 8 `spec_ckpt` calls. Claimed on AMD Strix Halo (gfx1151): no draft 32.4 t/s; spec before **6.2 t/s** (acceptance 0.54); spec after, n-max 3 / p-min 0.7, **41.5 t/s** (0.79); code with high acceptance at n-max 6, **56.6 t/s** (0.91). — [PR #28118](https://github.com/ggml-org/llama.cpp/pull/28118)
- **#31669 "GDN: use replay instead of rollback [WIP]"**: OPEN DRAFT, 2026-11-04, am17an. It replays GDN steps instead of snapshotting state per draft position. Recurrent-state memory drops 73-91% (n_rs_seq 7: 1197 → 177 MiB). Speed on an RTX PRO 6000 with Qwen3.8-27B: single-sequence DFlash2 flat (−0.1% to +0.5%); batched verify +0.9% (1 seq) up to +34.5% (32 seqs); prefill on Strix Halo (HIP) +0.9-1.7%. — [PR #31669](https://github.com/ggml-org/llama.cpp/pull/31669)
- **#31750 "llama: use KV-only graphs for MTP draft catch-up"**: OPEN DRAFT, 2026-11-05, ravel7524. Claimed on Qwen3.8-27B Q8_0, 2x RTX 5090, draft-mtp: depth 5 gives ~10% more t/s than the previous best of depth 3. — [PR #27173](https://github.com/ggml-org/llama.cpp/pull/27173)

For Qwen3.8-27B the draft head shrinks from 248320×5120 to 32768×5120. — [PR #31037](https://github.com/ggml-org/llama.cpp/pull/31037), [PR #31031](https://github.com/ggml-org/llama.cpp/pull/31031)

## Which PRs improve KV cache / prompt cache reuse speed for long contexts?

### Takeaway
Most prompt-cache work is server-side checkpoint handling for hybrid/SWA models, which is relevant because Qwen3.8-Flash-Next is a GDN hybrid that can only resume at checkpoints. Merged: reference-counted checkpoints (#30137), checkpoints preserved across slot save/restore (#26004), and the fixes in #30498 and #31350. Open: last-user-end checkpointing (#30745, reuse 91% → 94% per resent prompt), the tool-request checkpoint-invalidation fix (#24891, directly relevant to opencode tool calls), shared prefix cells across slots (#30970), a persistent disk cache (#28092), and the CUDA fix for slow prefill with q4_0 KV (#27140, 74 → 1182 t/s on RTX 3090).

### Cited Findings
- **#24891 "server: fix checkpoint invalidation after tool requests in multi-turn conversation"**: OPEN, 2026-06-22, last updated 2026-10-12. `n_past` from true prefix matching is overwritten by the smaller checkpoint value, which erases valid checkpoints. Generation-phase checkpoints also evict input-phase ones needed by the next request. Fixes #24890. — [PR #24891](https://github.com/ggml-org/llama.cpp/pull/24891); related open bug "Context checkpoints always invalidated on hybrid/recurrent models" — [Issue #24055](https://github.com/ggml-org/llama.cpp/issues/24055)
- **#30745 "server : let the last-user-end checkpoint supersede earlier ones"**: OPEN DRAFT, 2026-10-18. Checkpoints at the end of the last user message, where a resent prompt diverges. After 8 chat turns on a V100: Qwen3.8-27B with or without MTP, reuse **91% → 94%**, save file 3.63 → 0.80 GB. — [PR #30745](https://github.com/ggml-org/llama.cpp/pull/30745)
- **#30137 "llama-server: Use reference-counted checkpoints instead of deep-copies"**: MERGED 2026-11-05. Uses `shared_ptr` checkpoints and skips zero-init. The gain grows with context, especially for queued requests. Tested on 3x Arc Pro B60. — [PR #30137](https://github.com/ggml-org/llama.cpp/pull/30137). The older open #27451 does the same and hardens OOM handling. — [PR #27451](https://github.com/ggml-org/llama.cpp/pull/27451)
- **#26004 "server : preserve context checkpoints across slot save/restore"**: MERGED 2026-10-08. Hybrid models (Qwen3-Next) used to force a full re-prefill after restore. — [PR #26004](https://github.com/ggml-org/llama.cpp/pull/26004). Other merged server fixes: #30498/#30567/#30580 (2026-10-15) and #31350 "restore the spec checkpoint for drafts longer than n_rs_seq" (2026-10-29). — [PR #30498](https://github.com/ggml-org/llama.cpp/pull/30498), [PR #31350](https://github.com/ggml-org/llama.cpp/pull/31350)
- **#30970 "server : share prompt prefix cells between slots (--slot-attach)"**: OPEN, 2026-10-22. With a unified KV cache, a new request attaches to another slot's prefix cells without copying, even when that slot is busy. Hybrid models attach at a checkpoint, and the server adds a checkpoint where prompts diverge (at least 1024 tokens in). On by default. — [PR #30970](https://github.com/ggml-org/llama.cpp/pull/30970)
- **#28092 "server : add --cache-disk for a persistent prompt cache"** (OPEN, 2026-08-31) supports hybrid/SWA checkpoints, restores across restarts, and evicts LRU by disk size. **#29738 "session-keyed automatic slot save/restore"** (OPEN, 2026-09-30) keys slots on client session-id headers. — [PR #28092](https://github.com/ggml-org/llama.cpp/pull/28092), [PR #29738](https://github.com/ggml-org/llama.cpp/pull/29738)
- **#29918 "server : add --cache-reuse-hybrid for recurrent/hybrid models"**: OPEN DRAFT, 2026-10-03. Reuses the KV of text that survives a mid-prompt edit on hybrid models. The author has not reviewed the code. — [PR #29918](https://github.com/ggml-org/llama.cpp/pull/29918)
- **#27140 "Slow prefill on small KV quants fixed"**: OPEN, 2026-08-15. CUDA FA prefill with q4_0/q4_1/q5_x KV collapsed at long prompts. Claimed on 2x RTX 3090, Qwen 3.8 27B, ~9000-token prompt: **q4_0 74 → 1182 t/s**, with q8_0 already at 1159. Fixes #27109. NVIDIA-tested only. — [PR #27140](https://github.com/ggml-org/llama.cpp/pull/27140)
- **#31391 "cuda : gather batched tensor reads into mapped host memory"**: MERGED 2026-11-03. Saving a fragmented KV cache needed thousands of `cudaMemcpyAsync` calls; it now uses one gather kernel. This speeds up slot save and prompt-cache store. — [PR #31391](https://github.com/ggml-org/llama.cpp/pull/31391)
- **#31073 "kv-cache : keep rotation constants on the GPU"** (MERGED 2026-10-30) keeps Hadamard matrices resident, avoiding host trips on slow PCIe. — [PR #31073](https://github.com/ggml-org/llama.cpp/pull/31073). **#31539** (OPEN) stride-skips the contiguous slot search in `find_slot`. — [PR #31539](https://github.com/ggml-org/llama.cpp/pull/31539)

### Inferences
- For opencode (long growing prompts, tool calls), #24891 and #30745 are the most relevant open checkpoint fixes. On a hybrid model a missed checkpoint means re-prefilling from an earlier point, which costs seconds at our ~1.8k t/s prefill.
- With q4_0 K and long prompts, check whether Avalon on HIP suffers the q4_0 prefill collapse that #27140 fixed on CUDA. Avalon's measured 1.77k t/s at 16-32k suggests it does not, but that is not verified for q4_0 V.

### Gaps
- No prompt-cache PR reports HIP numbers. Gains are reported as reuse percentages or memory, not end-to-end TTFT for agent loops.
- Whether Avalon already contains #26004/#30137-equivalent logic was not verified (no `shared_ptr` checkpoint pattern was found by grep).
