### Why the model over-predicted (deferral: model +33%, measured +15.8% +-3.9)

The old model (`window_ms`) let layer l+1's router and the pool of layer l+1 run while layer l's late CPU rows were still
being computed. The engine does not: late rows are added to the residual **before layer l+1's FFN-side read**
(`late_add`, "pre(l+1) adds them to the residual before its FFN-side read"), so l+1's router, plan and doorbell wait for the
CPU, and the pool of l+1 starts after that. Only the next layer's **mixer** (attention / GDN, ~65% of the 15.75 ms) overlaps
the CPU. Error budget, one correction at a time (all on the edit window):

| Step | Deferral gain predicted |
| --- | ---: |
| 0 the 2026-11-09 model | +32.9% |
| 1 GPU pre-doorbell work 15.75 ms from the profile (was 11.5; the 4.3 ms of VRAM expert kernels hide behind the CPU wait), c recalibrated | +33.9% (no effect) |
| 2 late rows gate the next router and pool | +26.7% |
| 3 heavy rows (weight >= 0.1, BELOW default) stay on time, share 0.4 | +26.0% |
| 4 deferred-layer cost, fitted: 91 us per deferred layer | +14.3% |
| 5 bench window 1.0 ms longer than the profile's, promotion contention alpha 0.5 | **+15.8%** (measured +15.8) |

Which term was wrong, in order of size: (a) the layer chain (step 2, -7 points); (b) a per-layer deferral cost the model did
not have (step 4, -11.7 points): this is a **fitted** term, and the least certain one. It stands for the flag hand-off and the
pool's wake-up latency per deferred layer; it agrees in size with the rocprof of the deferral run
(`2026-11-09-gpuprof-defer/summary.txt`: `wait_flag_ge_kernel` 11,280 calls, 108.8 us each, 31% of kernel time), but it is
one fitted number absorbing everything unmodelled; (c) the heavy-row share barely matters once (b) is refitted.

Not the cause, checked:

- CPU expert time. The cost per distinct missed expert is the same in both profile windows: 17.41 ms / (7.44 x 48) = 48.7 us
  (edit) and 5.19 ms / (2.22 x 48) = 48.7 us (short). The model's c = 44.6 us (+ 40 us pool barriers per layer) is consistent
  with it. The old short-window rows (c = 15 us) were wrong because the one trace is edit-like (7.2 misses per layer, short
  windows have 2.2).
- Hit rate 81% vs 89%. The profile's edit windows are at 82% (8.88 CPU entries of 49.4), the trace is at 81.2%; 89% is the
  bench's overall figure (short windows: 91%). c is calibrated on measured CPU ms, so the deferral estimate does not depend on
  it. It does matter for the **policy** arms: see the hit-rate sensitivity in the candidate section.
- Draft acceptance. On edits it is 0.94-0.95 in every arm. It confounds short chat (0.74 vs 0.69, different text), not edits.
- The bench's edit window (4.70 tok/window / 116.6 tok/s = 40.3 ms) is 1.0 ms longer than the model's serial window
  (39.3 ms; profile 37.4), a small dilution.

k-th miss (model +14% over deferral, measured +2.0% +-1.6): promotions cost CPU time. 26.8 promotions per window for the tier
becomes 81.6 for KMISS 2/8, and the DMA (12 GB/s) takes DDR4 bandwidth from the pool (27 of 33 GB/s). With alpha = 0.5
(CPU ms lost per ms of DMA, about the 12/27 bandwidth ratio) the new chain predicts +2.7%; at alpha 0.25 it would be +6.2%,
at 0.75 -0.9%. The measurement bounds alpha to about 0.4-0.75.

### Caps and time saved

Thinking above cap + `reasoning_budget_grace` (512) is cut (the server closes at the next sentence or line end, at most 512 tokens
past the cap):

| Cap | Turns hit | Tokens cut | Time saved |
| --- | ---: | ---: | --- |
| 512 | 1 | 130 | 1.5 s total = 0.3% of turn time = 0.04 s per turn |
| 1,024 and above | 0 | 0 | 0 |

Proposal from p99 (1,061) with margin, provisional until the log has an effort field and >= 200 turns:
`low` 1,024, `medium` 1,536, `high` 3,072 (the family's table maps high, xhigh and max to the same level, so one `high` entry
covers them; with two names the first match wins). Expected saving on this log: 0 s per turn; the value of a cap is tail
protection (a runaway 8K-token think at ~90 tok/s is ~90 s; capped at 3,072 + 512 it is ~40 s), and the log has no such turn.
**Recommendation: do not change the default yet.**

### Where the cap is set, and the exact change (not applied)

Server option: `"reasoning_budget_by_effort"` in the preset JSON (`serve/server.py` `budget_by_effort_setting`, read at
server.py:11412, applied in `Service.reasoning_budget`, server.py:5305; commit 5dd620fb9). A request's own
`reasoning_budget_tokens` wins; an unlisted level falls back to the global `reasoning_budget_tokens` (unset in the presets);
0 means no cap for that level; the soft close is `reasoning_budget_grace` (512, already in every Flash-Next preset). In
`configs/pancake/flashnext-iq2_xs-fast-hip.json`, after the `"reasoning_budget_grace": 512,` line (line 109):

```

```

and the same line in the other `configs/pancake/flashnext-*.json` presets if wanted.

To get a real per-effort p99, add the level to the turn log (one line each, `serve/server.py`): in `_write_turn_log` (line 5348)
take `effort=None` and `line["effort"] = effort`; at the call site (line 7576) pass `self.request_effort(req)`
(and the applied `budget`, to see whether a cap fired).
